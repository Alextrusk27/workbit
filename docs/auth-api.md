# Auth API — `/api/v1/auth`

Беспарольная аутентификация: вместо пароля — email и одноразовый шестизначный код,
который приходит письмом. Паролей в системе нет вообще — ни при первом входе, ни при
последующих, ни в базе. Отдельной регистрации в продукте нет: экран один, а «регистрация»
и «вход» для пользователя неразличимы — первый запрос кода на новый email сам заводит
учётную запись. Доставка кода на почту и обмен кода на токены — два отдельных шага.
Вторая часть контракта — двухтокенная схема (access + refresh) — устроена так же, как
в любом другом REST API с cookie-сессией, и от способа входа не зависит.

Все тела запросов и ответов — JSON.

## Аутентификация

Токены выдаются заголовками `Set-Cookie` (не в теле ответа) и приходят обратно автоматически.
Браузер-клиент должен слать запросы с `credentials: 'include'`.

- **access** — короткоживущий JWT (минуты). Cookie `access_token`
  (`Path=/`, `HttpOnly`, `Secure`, `SameSite=Lax`). Уходит с каждым запросом к API;
  по нему аутентифицируются защищённые ручки. Fallback `Authorization: Bearer <accessToken>`
  поддержан для Swagger в dev.
- **refresh** — долгоживущий токен (30 дней). Cookie `refresh_token`
  (`Path=/api/v1/auth`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Max-Age=30д`).
  Уходит только на `/refresh` и `/logout`.

Рекомендуемый клиентский флоу: при `401` на защищённой ручке вызвать `/refresh`, получить новую
пару cookie и повторить запрос. Refresh **одноразовый** — после `/refresh` старое значение
становится недействительным; в ответе всегда приходит новый refresh (обе cookie перезаписываются).

Проверка «залогинен ли пользователь» — вызов `GET /me`: `200` значит сессия жива, `401` значит
нет (или истёк access и нужно дёрнуть `/refresh`).

## Эндпоинты

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| POST | `/request-code` | запрос кода входа: если email не встречался раньше, попутно заводит на него учётную запись | — |
| POST | `/verify-code` | проверка кода из письма, выдача пары токенов | — |
| GET | `/me` | профиль текущего пользователя | cookie `access_token` |
| POST | `/refresh` | обмен refresh-cookie на новую пару токенов | cookie `refresh_token` |
| POST | `/logout` | отзыв refresh-токена и очистка cookie | cookie `refresh_token` |
| DELETE | `/delete` | удаление аккаунта | cookie `access_token` |

## Запросы (DTO)

```java
record RequestCodeRequest(@NotBlank @Email String email, @AssertTrue boolean personalDataConsent, String captchaToken)
record VerifyCodeRequest(@NotBlank @Email String email, @NotBlank @Pattern("\\d{6}") String code)
```

`email` — непустая строка в формате email. `personalDataConsent` — согласие на обработку
персональных данных (чекбокс формы входа): `false` или отсутствие поля — `400` ещё до
обращения к сервису. `captchaToken` — токен Yandex SmartCaptcha; когда проверка капчи
включена на сервере, отсутствие или невалидность токена — `403` (см. «Поведение»).
`code` — ровно 6 цифр, как в письме
(символы вне `0-9` или длина, отличная от 6, — `400` ещё до обращения к сервису).

`/refresh` и `/logout` тела не принимают — refresh-токен берётся из cookie `refresh_token`.

## Ответы

`/me` возвращает `200` с телом:

```java
record UserResponse(String email, Instant created)
```

У остальных эндпоинтов тело ответа пустое; токены (где они выдаются) передаются в
заголовках `Set-Cookie`.

- `/verify-code`, `/refresh` — статус `200`, ставят cookie `access_token` и `refresh_token`.
- `/request-code` — пустое тело со статусом `200` (код ушёл на почту).
- `/logout`, `/delete` — статус `204`, гасят обе cookie (`Set-Cookie` с `Max-Age=0`).

## Поведение

- **`/request-code` заводит пользователя по факту первого обращения.** Если email
  встречается впервые, тут же создаётся учётная запись — без отдельного шага
  «регистрация», без подтверждения намерения. Если email уже известен, эндпоинт просто
  перевыдаёт код — тем же вызовом пользуется и первый вход, и кнопка «отправить код ещё
  раз». Разницы между «вошёл впервые» и «вошёл снова» для клиента нет: в обоих случаях
  ответ — пустой `200`, письмо с кодом уходит на почту.
- **Согласие на обработку персональных данных обязательно.** Каждый вызов `/request-code`
  несёт `personalDataConsent: true` — без него код не выдаётся (`400`). Дата и время первого
  согласия сохраняются у пользователя (`auth.users.personal_data_consent_at`) и последующими
  запросами кода не перезаписываются: фиксируется момент, когда согласие было дано впервые.
  Принятие Пользовательского соглашения отдельного поля не имеет — по тексту соглашения оно
  происходит самим фактом запроса кода.
- **Код живёт 15 минут, одноразовый, на него отведено 5 попыток.** Каждый новый вызов
  `/request-code` сразу гасит все предыдущие активные коды пользователя — действующим
  остаётся только последний, и у него всегда свежий счётчик попыток. Пять неверных
  попыток на код — код блокируется навсегда (`Too many attempts`), даже если шестой
  попыткой ввести правильное значение: разблокировать его нельзя, единственный выход —
  запросить новый код через `/request-code`.
- **`/verify-code`**: успешная проверка выдаёт пару токенов и попутно ставит пользователю
  `email_verified = true` — сам факт ввода кода из письма и есть доказательство владения
  почтой, отдельного шага «подтвердить email» в контракте больше нет. Если для email нет
  ни одного пользователя (код на него ни разу не запрашивали), ответ — тот же
  `401 Invalid code`, что и при неверном коде: единообразный ответ проще для клиента и не
  требует отдельной ветки на редкий случай. Остальные ошибки, тоже `401`: `Code has
  expired` — истёк 15-минутный TTL; `Too many attempts` — исчерпаны попытки текущего кода.
- **`/refresh`**: предъявление уже использованного (отозванного) refresh-токена трактуется как
  компрометация — отзываются все активные сессии пользователя, ответ `401`.
- **`/delete`** — физическое удаление: запись пользователя удаляется из БД, вместе с ней
  каскадами сносятся все refresh-токены и коды входа, сессии интервью с вопросами и ответами,
  фидбэк и отчёты. Восстановление невозможно, состояния «деактивирован» у аккаунта нет.
  Доступ отзывается сразу: принципал резолвится из БД на каждый запрос, поэтому ещё не
  истёкший access-токен перестаёт работать немедленно. Email освобождается — запрос кода
  на него снова заведёт учётную запись, но это будет новый пользователь, никак не связанный
  с прежним.
- **Автоудаление неактивных аккаунтов.** Отметка активности (`last_seen`) обновляется каждый раз,
  когда выдаётся пара токенов, — на `/verify-code` и `/refresh`. Ежедневная фоновая задача
  (в 3 часа ночи по времени сервера) находит аккаунты без активности 335 дней, шлёт на их email
  письмо-предупреждение и запоминает дату отправки; если за следующие 30 дней вход так и не
  состоялся, аккаунт удаляется физически — тем же способом, что и по `/delete`. Любая выдача
  токенов до истечения этих 30 дней снимает отметку предупреждения и отменяет удаление.
  Отдельного эндпоинта у этого механизма нет; для клиента он выглядит как исчезнувшая учётная
  запись: `/request-code` на тот же email не восстановит прежний аккаунт, а заведёт новый,
  никак не связанный с удалённым.
- **Капча.** `/request-code` защищён Yandex SmartCaptcha от ботов, массово подставляющих
  чужие адреса. Клиент проходит невидимую проверку и передаёт полученный токен в
  `captchaToken`; сервер валидирует его запросом к SmartCaptcha (токен одноразовый — на
  каждый вызов, включая «отправить код ещё раз», нужен свежий). Проверка включается
  переменной `CAPTCHA_ENABLED` (ключ — `CAPTCHA_SERVER_KEY`); при выключенной капче поле
  игнорируется. Непройденная проверка или отсутствие токена при включённой капче — `403`
  с деталью `Captcha validation failed`. Если сам сервис SmartCaptcha недоступен, запрос
  пропускается без проверки — недоступность капчи не должна останавливать вход.
- **Лимит частоты.** `/request-code` ограничен по IP — не более 5 запросов за 15 минут
  (настраивается через `RATE_LIMIT_LIMIT` / `RATE_LIMIT_WINDOW`). `/verify-code` — отдельный,
  более широкий бакет: 10 запросов за 15 минут (`VERIFY_CODE_RATE_LIMIT_LIMIT` /
  `VERIFY_CODE_RATE_LIMIT_WINDOW`), потому что общий дефолт легко исчерпать легитимными
  опечатками при вводе кода. При превышении любого из лимитов — `429`.

## Ошибки

Тело ошибки:

```json
{
  "timestamp": "2026-06-16T12:00:00",
  "status": "UNAUTHORIZED",
  "message": "Bad credentials",
  "errors": ["Invalid code"]
}
```

| Код | Когда |
|---|---|
| `400` | невалидное тело запроса (нарушение ограничений полей, битый JSON) |
| `401` | код неверен, истёк или исчерпаны попытки (`/verify-code`); refresh-токен отсутствует, недействителен или уже использован (`/refresh`); нет токена или токен недействителен (`/me`, `/delete`) |
| `403` | проверка капчи не пройдена при включённой SmartCaptcha (`/request-code`, деталь `Captcha validation failed`) |
| `429` | превышен лимит частоты запросов с одного IP (`/request-code`, `/verify-code`) |
