# Billing API — `/api/v1/billing`

Домен квот тарифа и его оплаты. Показывает текущее состояние тарифа, списывает остатки, когда
пользователь тратит интервью или тренировку в других доменах, и проводит оплату тарифа через
Робокассу. Отдельной ручки «сменить тариф» нет — покупка любого платного тарифа идёт одним и
тем же сценарием оплаты, см. раздел «Продукты и цены» и блок «Оплата тарифа» ниже.

У каждого пользователя есть один тариф и два счётчика остатков: интервью и тренировки.
Остатки выдаются на тарифный период и сгорают вместе с его истечением. Разовых пакетов сверх
тарифа нет — докупка при исчерпании квоты устроена как повторная покупка тарифа: подробное
правило начисления — в блоке «Оплата тарифа».

## Тарифная сетка

Единственный источник сетки в коде — `enum BillingAccount.Plan`; здесь она приведена для
справки:

| Тариф | Интервью | Тренировки |
|---|---|---|
| `FREE` | 1 | 3 |
| `PRO` | 10 | 20 |
| `MAX` | 25 | 50 |

## Продукты и цены

Купить можно только платный тариф целиком, на 30 дней. Что именно покупается, определяет код
продукта; цена и план, в который он превращается после оплаты, жёстко зашиты в
`enum Payment.Product` на сервере — с клиента принимается только код продукта:

| Код продукта | Тариф | Цена |
|---|---|---|
| `PLAN_PRO` | `PRO` | 790.00 ₽ |
| `PLAN_MAX` | `MAX` | 1290.00 ₽ |

## Эндпоинты

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| GET | `/quota` | текущий тариф и остатки квот | cookie `access_token` (JWT) |
| GET | `/usage` | статистика лимитов и история операций — для страницы настроек | cookie `access_token` (JWT) |
| POST | `/payments` | создать платёж за тариф и получить URL платёжной страницы Робокассы | cookie `access_token` (JWT) |
| GET | `/payments/{id}` | статус платежа — для поллинга после возврата с платёжной страницы | cookie `access_token` (JWT) |
| POST | `/robokassa/result` | webhook Робокассы (ResultURL): уведомление об оплате | — (публичная ручка, `permitAll` в SecurityConfig; фронт её не вызывает) |

`GET /quota` и `GET /usage` только читают состояние. Списание остатков и проверка тарифа
происходят внутри других доменов — `interview` и `training` — при создании и перезапуске сессий;
см. раздел «Где всплывают 402 и 403» ниже. `POST /payments` и `GET /payments/{id}` — ручки для
фронта: запустить оплату и опросить её статус после возврата с платёжной страницы.
`POST /robokassa/result` фронт не вызывает никогда — на неё ходит сама Робокасса, когда оплата
прошла или не прошла; подробности в блоке «Оплата тарифа» раздела «Поведение».

## Запросы (DTO)

```java
record PaymentCreateRequest(@NotNull Payment.Product product)
```

`product` — код покупаемого продукта, один из `PLAN_PRO`/`PLAN_MAX` (см. «Продукты и цены»
выше). Поле обязательно: отсутствие или `null` — `400` ещё до обращения к сервису. Цену и план
сервер берёт из `Payment.Product` по этому коду — сумма или тариф с клиента не принимаются и
подменить их нельзя.

`GET /payments/{id}` тела не принимает — `id` платежа приходит в пути.

Webhook `POST /robokassa/result` — не JSON, а `application/x-www-form-urlencoded`, как это
устроено у Робокассы: три обязательных параметра формы, `OutSum`, `InvId`, `SignatureValue`.
Отдельного DTO с bean-валидацией у него нет — разбор и все проверки (подпись, сумма,
существование платежа) сделаны внутри `PaymentService.confirm`.

## Ответы

`GET /quota` возвращает `200` с телом:

```java
record QuotaResponse(
    Plan plan,                 // FREE | PRO | MAX
    Instant planExpiresAt,     // окончание оплаченного периода (UTC); null на FREE
    int planInterviewsLeft,    // остаток интервью по тарифу
    int planTrainingsLeft      // остаток тренировок по тарифу
)
```

Пример:

```json
{
  "plan": "FREE",
  "planExpiresAt": null,
  "planInterviewsLeft": 1,
  "planTrainingsLeft": 3
}
```

Тело всегда одно и то же для любого пользователя — ошибок «нет тарифа» не бывает (см. ниже).

`GET /usage` возвращает `200` с телом:

```java
record UsageResponse(
    UsageCounter interviews,           // счётчик интервью текущего тарифа
    UsageCounter trainings,            // счётчик тренировок текущего тарифа
    List<UsageEventResponse> events    // история операций, новые первыми
)

record UsageCounter(
    int left,    // остаток
    int total    // выдано всего
)

record UsageEventResponse(
    Instant at,             // момент операции (UTC)
    UsageEvent.Kind kind,   // SPEND | CREDIT
    UsageEvent.Target target, // INTERVIEW | TRAINING
    int delta,              // величина операции, всегда положительная
    String label            // готовое описание для показа пользователю
)
```

Пример:

```json
{
  "interviews": { "left": 0, "total": 1 },
  "trainings": { "left": 2, "total": 3 },
  "events": [
    {
      "at": "2026-08-12T09:15:00Z",
      "kind": "SPEND",
      "target": "TRAINING",
      "delta": 1,
      "label": "Тренировка — Spring Boot, Уверенный"
    },
    {
      "at": "2026-08-10T14:02:00Z",
      "kind": "SPEND",
      "target": "INTERVIEW",
      "delta": 1,
      "label": "Интервью — Java-разработчик"
    }
  ]
}
```

Тело тоже всегда одно и то же по форме — пользователь без единой операции получит полные
счётчики FREE и пустой `events`, а не ошибку.

`POST /payments` возвращает `200` с телом:

```java
record PaymentCreateResponse(
    UUID paymentId,   // идентификатор платежа для последующего поллинга статуса
    String paymentUrl // URL платёжной страницы Робокассы, куда нужно отправить пользователя
)
```

`GET /payments/{id}` возвращает `200` с телом:

```java
record PaymentStatusResponse(
    Payment.Status status,   // PENDING | PAID | FAILED
    Payment.Product product  // PLAN_PRO | PLAN_MAX
)
```

Сразу после создания статус всегда `PENDING`; в `PAID` платёж переводит подтверждение оплаты —
обычно webhook Робокассы, а если уведомление не дошло, то фоновая сверка (см. «Оплата тарифа»
ниже). `FAILED` в модели предусмотрен, но ни один код в проекте в него платёж не переводит —
брошенный или не прошедший оплату платёж так и остаётся `PENDING` бессрочно, отдельного
механизма отмены или протухания нет.

`POST /robokassa/result` отвечает не JSON, а простым текстом (`Content-Type: text/plain`):
строка `OK{InvId}`, где `{InvId}` — номер счёта из уведомления. Это не сообщение для человека,
а формат, которого требует протокол Робокассы: без ответа ровно такого вида она сочтёт
уведомление недоставленным и повторит его.

## Поведение

- **Строка тарифа ленивая.** У пользователя, который ни разу не тратил интервью или тренировку,
  строки в `billing.account` нет вовсе — `GET /quota` отдаёт виртуальный дефолт FREE
  (1 интервью, 3 тренировки), ничего не записывая в БД. Строка физически создаётся
  только первым списанием (`debitInterview`/`debitTraining`), тоже как FREE с полной квотой —
  так домен не плодит записи на каждое чтение остатков.
- **Истёкший платный тариф читается как FREE.** Если `plan_expires_at` в прошлом, и на чтении
  (`GET /quota`), и при списании PRO/MAX ведёт себя как FREE с нулевыми остатками —
  `planInterviewsLeft`/`planTrainingsLeft` отдаются `0`, `plan` в ответе меняется на `FREE`,
  `planExpiresAt` — на `null`.
- **Списание — атомарный условный `UPDATE`, гонки безопасны.** Каждое списание — это
  `UPDATE ... SET x = x - 1 WHERE ... x > 0` одним запросом, без чтения-потом-записи: две
  параллельные попытки потратить последнюю единицу квоты не могут обе решить, что она ещё есть, —
  вторая просто не найдёт строку под условие и получит `0` затронутых строк, что и трактуется
  как исчерпание.
- **Списание происходит в момент создания/перезапуска сессии, не при чтении квоты.** Перед
  дорогим вызовом LLM (генерация вопросов интервью или тренировки) есть мягкая предварительная
  проверка — `checkInterviewAvailable`/`checkTrainingAvailable` читает эффективную квоту и рубит
  запрос `402`-м до траты токенов, если остатков уже явно нет. Настоящее списание происходит
  позже, первой инструкцией той же транзакции, что создаёт сессию, — так что между мягкой
  проверкой и списанием возможна гонка (кто-то ещё успел потратить последнюю единицу), но она
  безопасна: атомарный `UPDATE` просто не сработает, и создание сессии всё равно упадёт `402`,
  просто уже после того, как LLM была вызвана впустую. Перезапуск завершённой тренировки
  (`POST /training/sessions/{id}/restart`) вопросы у LLM не запрашивает и списывает тренировку
  сразу, без мягкой предварительной проверки.
- **Стабильные строки ошибок для фронта.** Все точки списания и гейты отдают предсказуемый текст
  первым (и единственным) элементом `errors` в теле `ApiError` — фронт может ветвиться по нему:
  `"Interview quota exhausted"`, `"Training quota exhausted"` (обе — `402`,
  `PaymentRequiredException`) и `"Paid plan required"` (`403`, `ForbiddenException`).
- **`total` в `/usage` — это не то же самое, что `left` в `/quota`.** `total` — сколько
  единиц эффективный тариф выдаёт за период (сетка из раздела «Тарифная сетка» выше;
  1/3 у FREE и т.д.), `left` — сколько из них ещё не потрачено. У пользователя без строки
  `billing.account` (ни разу ничего не тратил) отдаётся полная FREE-квота — `left = total`, как и
  виртуальный дефолт `GET /quota`. У истёкшего платного тарифа `left`/`total` — оба `0`:
  в текущем периоде по факту больше ничего не выдано, показывать «выдано N, осталось 0» было бы
  неверно.
- **История операций (`events`) — полная, без пагинации и без фильтров.** Ручка отдаёт все
  записи `billing.usage_event` пользователя разом, новые первыми (сортировка по `at desc`).
  Событие пишется одной строкой при каждом успешном списании — создании сессии интервью, создании
  или перезапуске сессии тренировки — тем же вызовом, что уменьшает счётчик (`saveSpendEvent`
  внутри `debitInterview`/`debitTraining`), поэтому список событий и текущие остатки всегда
  согласованы. `delta` в `UsageEventResponse` всегда `1` и всегда положительна — какая это
  операция, списание или начисление, видно по `kind`, а не по знаку числа. `label` — уже готовая
  для показа строка: `"Интервью — {название вакансии}"` или `"Тренировка — {навык}, {уровень}"`
  (русский лейбл уровня сложности, как в `docs/training-api.md`), собирается на бэке, локализовать
  или собирать из отдельных полей на фронте не нужно.
- **`CREDIT`-события пишет только подтверждённая оплата тарифа.** Единственный источник
  начислений — webhook Робокассы; начислить квоту в обход оплаты в контракте нельзя. Одна
  успешная оплата пишет сразу два `CREDIT`-события — по интервью и по тренировкам, — с
  одинаковыми `at` и `label`: фронт может группировать их в `/usage` в одну пачку по этой паре
  полей, а не показывать двумя отдельными строками. `label` — текст купленного продукта, например
  `"Тариф «Про» на 30 дней"`.

### Оплата тарифа

- **Создание платежа не проверяет, есть ли у пользователя уже тариф.** `POST /payments` всегда
  создаёт новую запись в статусе `PENDING` и новый `paymentUrl` — купить `PLAN_PRO` можно и с
  уже активным `PRO`, и с активным `MAX`. Что в итоге получит пользователь, решает правило
  начисления при подтверждении оплаты (см. ниже), а не сама точка создания платежа.
- **Редирект на `paymentUrl` уводит пользователя на страницу Робокассы, а не на бэкенд.** Дальше
  он платит на её стороне. Success/Fail URL, куда Робокасса вернёт его после оплаты или отказа,
  ведут на страницы фронта (`/app/billing/success`, `/app/billing/fail`) и сами по себе никаких
  начислений не делают — это чисто UX-редирект. Единственный источник истины о результате оплаты
  — webhook `POST /robokassa/result`.
- **Между возвратом пользователя и подтверждением оплаты возможна задержка.** Робокасса шлёт
  webhook независимо от того, когда (и вернётся ли вообще) пользователь на Success URL — обычно
  раньше, но гарантии порядка нет. Поэтому `GET /payments/{id}` существует для поллинга: пока
  webhook не обработан, статус — `PENDING`, даже если пользователь уже видит страницу успеха.
  Фронту нужно опрашивать ручку до появления `PAID` (или явно показывать состояние «обрабатываем
  оплату»), а не считать оплату завершённой по самому факту редиректа.
- **Webhook доверяет уведомлению только после проверки подписи и суммы.** Подпись считается как
  SHA256 от `OutSum:InvId:Пароль#2` и сравнивается с присланной константным временем
  (`MessageDigest.isEqual`), без учёта регистра — так закрывается подделка уведомлений в обход
  Робокассы. Дальше платёж ищется по `InvId`, и полученный `OutSum` сверяется с суммой, записанной
  при создании платежа. Любое из трёх — неверная подпись, неизвестный `InvId`, несовпавшая сумма
  — даёт `400`; по протоколу Робокассы это сигнал повторить доставку уведомления, а не
  окончательный отказ.
- **Подтверждение оплаты идемпотентно.** Переход в `PAID` — условный `UPDATE ... WHERE status =
  'PENDING'`. Если Робокасса (как и положено по её протоколу) продублирует уже обработанное
  уведомление, второй вызов не найдёт строку под условие, начисление не повторится, а ответ
  всё равно будет `OK{InvId}` — повторное уведомление по уже оплаченному платежу для Робокассы
  выглядит так же успешно, как и первое.
- **Начисление тарифа — та же транзакция, что подтверждение оплаты.** Правило одно на все случаи:
  план становится купленным (`Payment.Product.plan`). Если у пользователя уже активный платный
  тариф (не `FREE` и срок ещё не истёк), срок продлевается на 30 дней от текущего
  `planExpiresAt`, а квота купленного тарифа прибавляется к тому, что осталось от старого. Если
  тариф неактивен (`FREE` или истёкший платный), срок ставится как момент оплаты + 30 дней, а
  квота выдаётся с нуля по сетке купленного тарифа — остаток `FREE` при этом не переносится.
  Одно и то же правило одинаково обслуживает первую покупку, продление того же тарифа и переход
  Про ↔ Макс — отдельной логики «смена тарифа» в контракте нет.
- **Потерянный webhook подхватывает фоновая сверка.** Раз в минуту бэкенд опрашивает Робокассу
  (XML-интерфейс `OpStateExt`) по каждому платежу, который висит в `PENDING` от 30 секунд до
  суток, и, если операция там значится успешной, подтверждает его сам — тем же идемпотентным
  переходом и с тем же начислением, что и webhook. Для фронта это прозрачно: `PAID` в
  `GET /payments/{id}` просто появится на очередном опросе. Ограничение Робокассы: `OpStateExt`
  не отдаёт тестовые платежи, поэтому в тестовом режиме (`IsTest=1`) сверка отключена и оплату
  подтверждает только webhook.

## Где всплывают 402 и 403

Сам billing только читает состояние (`GET /quota`, `GET /usage`), но проверки квоты встроены в
ручки создания сессий в `interview` и `training` — именно там пользователь и увидит нехватку
квоты:

| Ручка | Код | Условие | `errors[0]` |
|---|---|---|---|
| `POST /api/v1/interview/sessions` | `402` | остаток интервью по тарифу `0` | `Interview quota exhausted` |
| `POST /api/v1/training/sessions` | `402` | остаток тренировок по тарифу `0` | `Training quota exhausted` |
| `POST /api/v1/training/sessions/{sessionId}/restart` | `402` | остаток тренировок по тарифу `0` | `Training quota exhausted` |
| `POST /api/v1/training/sessions/{sessionId}/questions/more` | `403` | эффективный тариф пользователя — `FREE` (в том числе истёкший PRO/MAX) | `Paid plan required` |

Добор вопросов в тренажёре (`.../questions/more`) требует платного тарифа, но саму квоту
тренировок не списывает — это гейт по тарифу, а не расход остатка.

## Ошибки

Тело ошибки — общий для всего API формат:

```json
{
  "timestamp": "2026-06-16T12:00:00",
  "status": "PAYMENT_REQUIRED",
  "message": "Payment required.",
  "errors": ["Interview quota exhausted"]
}
```

Коды, достижимые на `GET /quota` и `GET /usage`:

| Код | Когда |
|---|---|
| `401` | нет токена или токен недействителен |

Коды, достижимые на `POST /payments`:

| Код | Когда |
|---|---|
| `400` | тело без поля `product` (`errors[0]`: `Product is required`) либо с нераспознанным значением (стандартная ошибка разбора JSON от `ExceptionController`: `Invalid value for field 'product': ...`) |
| `401` | нет токена или токен недействителен |

Коды, достижимые на `GET /payments/{id}`:

| Код | Когда |
|---|---|
| `401` | нет токена или токен недействителен |
| `404` | платежа с таким `id` нет либо он принадлежит другому пользователю — ответ в обоих случаях один и тот же, различить их с фронта нельзя |

Коды, достижимые на `POST /robokassa/result`:

| Код | Когда |
|---|---|
| `400` | неверная подпись, неизвестный `InvId` или несовпавшая сумма — по протоколу Робокассы `400` означает «повтори доставку уведомления» |

Эта ручка отдаёт `400`, а не `401`/`403`, хотя и открыта без авторизации: доступ к ней защищает
не кука, а подпись запроса, поэтому чужой или поддельный вызов — это невалидные данные, а не
