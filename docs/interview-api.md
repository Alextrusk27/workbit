# Interview API — `/api/v1/interview`

AI-интервью по конкретной вакансии hh.ru: пользователь присылает ссылку на вакансию, бэкенд
подтягивает её данные с hh.ru и генерирует через LLM набор вопросов под эту вакансию (с учётом
названия, работодателя, ключевых навыков и описания). Вопросы выдаются пользователю по одному;
после каждого ответа LLM может — но не обязана — задать до двух уточняющих вопросов по этому же
ответу. Завершить интервью можно только ответив на **все** основные вопросы — в отличие от
тренажёра (`docs/training-api.md`), досрочного финиша здесь нет. При завершении LLM разбирает
все ответы (с учётом уточнений) кейсами и формирует отчёт: оценку по каждому основному вопросу,
средний балл, оценку вероятности оффера и рекомендации, что проработать перед реальным
собеседованием. Все тела запросов и ответов — JSON.

Домен во многом зеркалит тренажёр (сессия → вопросы по одному → уточнения → отчёт), но не
разделяет с ним ни данные, ни правила: здесь нет профессии/темы, вопросы не берутся из банка,
а полностью генерируются LLM под конкретную вакансию, и порог для завершения — не «минимум N
ответов», а «отвечены все».

## Доступ

Домен закрыт целиком: `SecurityConfig` требует аутентификации на любой путь, не входящий
в `/api/v1/auth/**` и Swagger. Ко всем ручкам `/api/v1/interview/**` (и, отдельно, к ручкам
вакансий `/api/v1/vacancies/**` — см. ниже) нужен валидный access-токен — cookie `access_token`
(для Swagger в dev поддержан fallback `Authorization: Bearer <accessToken>`). Без него — `401`
с пустым телом (это делает Security-фильтр, а не контроллер, поэтому тело `ApiError` не
приходит).

Сессии и вопросы привязаны к пользователю из токена. Большинство ручек (получение сессии,
список, следующий вопрос, завершение, отчёт, удаление) сами ищут ресурс с учётом `userId`,
поэтому чужой ресурс для них просто «не существует» — ответ `404`. Исключение — отправка ответа
(`POST .../questions/{questionId}`): там вопрос сначала ищется по `questionId` без учёта
владельца, и если он оказывается чужим, это разбирается явно — ответ `403`.

## Эндпоинты

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| POST | `/sessions` | создать сессию интервью по ссылке на вакансию | cookie `access_token` |
| GET | `/sessions` | список сессий текущего пользователя | cookie `access_token` |
| GET | `/sessions/{sessionId}` | получить сессию по id | cookie `access_token` |
| POST | `/sessions/{sessionId}/questions/next` | получить текущий неотвеченный вопрос (основной или уточняющий) | cookie `access_token` |
| POST | `/sessions/{sessionId}/questions/{questionId}` | отправить ответ на вопрос | cookie `access_token` |
| POST | `/sessions/{sessionId}/finish` | завершить интервью и сформировать отчёт | cookie `access_token` |
| GET | `/sessions/{sessionId}/report` | получить ранее сформированный отчёт | cookie `access_token` |
| DELETE | `/sessions/{sessionId}` | удалить сессию вместе с вопросами, ответами и отчётом | cookie `access_token` |

## Справочные значения

- **`InterviewSession.Status`** — `CREATED`, `IN_PROGRESS`, `COMPLETED`. Кастомного лейбла нет,
  сериализуется по имени константы (как `TrainingSession.Status`).
- **`InterviewReport.OfferProbability`** — сериализуется не по имени, а по русскому лейблу через
  `@JsonValue`: `LOW` → `"Низкая"`, `MEDIUM` → `"Средняя"`, `HIGH` → `"Высокая"`. Приходит только
  в отчёте, в запросах этого поля нет.

## Запросы (DTO)

```java
record CreateInterviewSessionRequest(@NotBlank String vacancyUrl)

record SubmitAnswerBody(@NotBlank String answerText)
```

`vacancyUrl` — ссылка на вакансию hh.ru; из неё регулярным выражением вычленяется числовой id
вакансии (`hh\.ru/vacancy/(\d+)`, поиск подстроки, а не сверка со всей строкой). Поддомены вида
`spb.hh.ru`, `hh.kz` и т.п. проходят так же, как `hh.ru`, лишь бы в строке нашлась эта подстрока;
протокол (`http`/`https`) не проверяется. Ссылка, не подходящая под этот паттерн, — `400`. Сама
вакансия при этом валидируется отдельно: если по вычлененному id hh.ru вернул 404 или пометил
вакансию архивной — `404`, а не `400` (ссылка синтаксически валидна, но вакансии недоступны).

`POST .../questions/next`, `POST .../finish`, `GET .../report` и `DELETE` тела не принимают.

Пример `CreateInterviewSessionRequest`:

```json
{
  "vacancyUrl": "https://hh.ru/vacancy/123456"
}
```

## Ответы

```java
record InterviewSessionResponse(
    UUID id, String vacancyName, String employer, String vacancyUrl, String experience,
    InterviewSession.Status status, int answeredCount, int totalQuestions,
    Instant created, Instant completedAt)

record InterviewQuestionResponse(
    UUID questionId, int orderIndex, String questionText, boolean followUp,
    String answerText, Integer score, String feedback)

record InterviewReportResponse(
    UUID reportId, UUID sessionId, Double avgScore, InterviewReport.OfferProbability offerProbability,
    String overallFeedback, String recommendations, Instant generatedAt,
    List<InterviewQuestionResponse> questions)
```

- **`POST /sessions`** — `201` с `InterviewSessionResponse` и заголовком `Location`
  (`/sessions/{id}`). Свежесозданная сессия: `status = CREATED`, `answeredCount = 0`,
  `totalQuestions` — сколько основных вопросов реально сгенерировала LLM (от 5 до 20, см.
  «Поведение»). `vacancyName`/`employer`/`vacancyUrl`/`experience` берутся из только что
  сохранённого снапшота вакансии; `vacancyUrl` в ответе — всегда канонический вид
  `https://hh.ru/vacancy/{id}`, даже если в запросе была ссылка на поддомен или с лишними
  query-параметрами. `experience` — как есть в вакансии hh.ru (например, «От 1 года до 3 лет»),
  `null`, если в вакансии не указан. Список вопросов в ответе нет — они уже сгенерированы на
  бэке, но, как и в тренажёре, отдаются по одному через `.../questions/next`.
- **`GET /sessions`** — `200`, `List<InterviewSessionResponse>` — все сессии текущего
  пользователя целиком, без пагинации (в отличие от `training`, где та же ручка отдаёт
  `PagedModel`). Порядок в запросе репозитория не задан явно (нет `ORDER BY`), так что полагаться
  на «новые сначала» не стоит, даже если так выглядит на практике.
- **`GET /sessions/{sessionId}`** — `200`, `InterviewSessionResponse` с актуальным
  `answeredCount`.
- **`POST .../questions/next`** — `200`, `InterviewQuestionResponse`. Возвращает неотвеченный
  вопрос: сначала уже сгенерированный неотвеченный уточняющий (если есть), иначе — уточнение,
  которое LLM решит задать по последнему ответу, иначе — следующий неотвеченный основной вопрос
  из набора, подготовленного при создании сессии. `answerText`, `score`, `feedback` для только
  что полученного вопроса всегда `null` — по ходу интервью оценок нет.
- **`POST .../questions/{questionId}`** — `204`, пустое тело. Фидбэка в ответе нет — оценка
  появится только в отчёте после `finish`.

  `score`/`feedback` в `InterviewQuestionResponse` относятся не к отдельному вопросу, а к кейсу
  целиком (основной вопрос + его уточнения — см. «Поведение»): после `finish` они заполняются у
  основного вопроса кейса и описывают разбор всего кейса, включая ответы на уточнения. Сами
  уточняющие вопросы в отчёт не попадают — при завершении сессии они удаляются (см.
  «Поведение»), поэтому `InterviewReportResponse.questions` состоит только из основных вопросов
  (`followUp: false` у каждого элемента).
- **`POST .../finish`** — `201` с `InterviewReportResponse` и заголовком `Location`
  (`/sessions/{id}/report`).
- **`GET .../report`** — `200`, `InterviewReportResponse`.
- **`DELETE /sessions/{sessionId}`** — `204`, пустое тело.

Пример `InterviewSessionResponse` (свежесозданная сессия):

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "vacancyName": "Java-разработчик",
  "employer": "ООО Ромашка",
  "vacancyUrl": "https://hh.ru/vacancy/123456",
  "experience": "От 1 года до 3 лет",
  "status": "CREATED",
  "answeredCount": 0,
  "totalQuestions": 12,
  "created": "2026-07-28T10:00:00Z",
  "completedAt": null
}
```

Прогресс «5/10» на фронте — это `answeredCount`/`totalQuestions`; уточняющие вопросы в оба поля
не входят.

Пример `InterviewQuestionResponse` (неотвеченный уточняющий вопрос):

```json
{
  "questionId": "b6b6c1c2-2222-4a3a-9a3a-000000000002",
  "orderIndex": 1,
  "questionText": "Вы упомянули пул соединений — а как вы выбирали его размер?",
  "followUp": true,
  "answerText": null,
  "score": null,
  "feedback": null
}
```

Пример `InterviewReportResponse`:

```json
{
  "reportId": "b6b6c1c2-1111-4a3a-9a3a-000000000001",
  "sessionId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "avgScore": 3.8,
  "offerProbability": "Средняя",
  "overallFeedback": "Кандидат уверенно ориентируется в основах, но...",
  "recommendations": "Перед собеседованием стоит повторить типы блокировок и explain analyze.",
  "generatedAt": "2026-07-28T12:00:00Z",
  "questions": [
    {
      "questionId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
      "orderIndex": 1,
      "questionText": "Расскажите про индексы в PostgreSQL",
      "followUp": false,
      "answerText": "Использую индексы и explain analyze...",
      "score": 4,
      "feedback": "Ответ по существу, но не хватило деталей про покрывающие индексы. Уточнение про explain analyze раскрыто хорошо."
    },
    {
      "questionId": "b6b6c1c2-2222-4a3a-9a3a-000000000002",

      "followUp": false,

```

Как и в тренажёре, первый вопрос выше — целый кейс (основной вопрос + оценённое уточнение про
`explain analyze`, текст которого в отчёт не попадает), а второй — пример кейса, который LLM не
успела оценить: `score`/`feedback` тогда остаются `null` даже в уже сформированном отчёте. Это
допустимо, пока в целом оценена как минимум половина кейсов — иначе `finish` завершится `503`
(см. «Ошибки»).

## Поведение

- **Создание сессии полностью синхронно с генерацией вопросов.** `POST /sessions` тремя шагами:
  забирает данные вакансии с hh.ru (`VacancyService.fetch`), одним вызовом LLM генерирует под
  неё набор основных вопросов, сохраняет неизменный снапшот вакансии и сами вопросы. Всё это —
  один HTTP-запрос; ответ приходит только когда вопросы уже готовы, отдельного «прогресса
  генерации» нет.
- **Вакансия сохраняется как неизменный снапшот на момент создания сессии.** Данные о вакансии
  внутри уже созданной сессии не обновляются, даже если объявление на hh.ru потом изменится или
  будет снято с публикации. Чтобы узнать актуальный статус вакансии прямо сейчас — отдельная
  ручка `GET /api/v1/vacancies/status` (см. ниже), она саму сессию никак не трогает.
- **Сложность вопросов подстраивается под требуемый вакансией опыт.** hh.ru отдаёт опыт строкой
  (например, «Нет опыта», «От 1 года до 3 лет», «От 3 до 6 лет», «Более 6 лет»), и по ней бэкенд
  выбирает один из четырёх грейдовых наборов LLM-агентов — noexp/junior/middle/senior — для
  генерации вопросов, решения об уточнениях и итогового ревью. Сам текст опыта в промпты не
  передаётся отдельным полем — грейд уже зашит в выбранного агента; любой не распознанный или
  отсутствующий вариант трактуется как junior.
- **Количество основных вопросов не фиксировано.** LLM просят сгенерировать от 5 до 20 вопросов
  под вакансию; после фильтрации пустых ответов и обрезки лишних сверх 20 вопросов в сессии
  может оказаться от 5 до 20 — ровно столько, сколько реально пригодилось. Если LLM вернула
  меньше 5 пригодных вопросов — `503`, сессия не создаётся. `totalQuestions` фиксируется в
  момент создания и дальше не меняется.
- **`.../questions/next` идемпотентен.** Уже заданный, но неотвеченный уточняющий вопрос ручка
  вернёт как есть, не обращаясь к LLM повторно. Это и точка возврата: прервал интервью и
  вернулся — повторный вызов даст тот же вопрос, на который ещё нет ответа.
- **Во время незавершённого интервью истории ответов нет.** API отдаёт только один текущий
  неотвеченный вопрос за раз; ручки со списком уже отвеченных вопросов и промежуточных оценок в
  домене нет. Полная история (вопрос, ответ, оценка) становится доступна только после `finish` —
  через сам ответ `finish` или `GET .../report`.
- **Уточняющие вопросы.** После каждого ответа бэкенд **ровно один раз** спрашивает LLM, стоит
  ли задать уточнение по этому кейсу; решение (любое — и «спросить», и «не спрашивать»)
  фиксируется флагом в БД. Поэтому повторные вызовы `next` (например, после перезагрузки
  страницы) не приводят ни к повторному платному обращению к LLM, ни к тому, что LLM «передумает»
  и подсунет уточнение к уже пройденному вопросу. Контекст уточнения — только текущий кейс:
  основной вопрос, ответ на него и прошлые уточнения этого же кейса; название вакансии в запрос
  попадает, вся история сессии — нет. На кейс приходится не больше **2** уточнений
  (`MAX_FOLLOW_UPS_PER_QUESTION` в `InterviewService`, меньше, чем в тренажёре, где лимит 4) —
  лимит держит бэкенд, при его достижении LLM не спрашивают вовсе. Пустой текст уточнения от LLM
  трактуется как «не спрашивать», а не как ошибка. Уточняющие вопросы не входят ни в
  `totalQuestions`, ни в `answeredCount`.
- **`orderIndex` считается по-разному** у основных и уточняющих: у основного — номер вопроса в
  сессии (1..N), у уточняющего — номер внутри своего кейса (1..2). Сквозной нумерации по сессии у
  уточнений нет.
- **Оценок по ходу интервью нет.** `POST .../questions/{questionId}` только сохраняет текст
  ответа и отвечает `204` без `score`/`feedback`. Весь фидбэк формируется одним пакетом при
  завершении. Повторно ответить на уже отвеченный вопрос нельзя — `409`. Как только сохранён
  первый ответ, статус сессии переходит из `CREATED` в `IN_PROGRESS`.
- **Проверка принадлежности вопроса.** Помимо владельца, у отправки ответа проверяется, что
  `questionId` действительно относится к сессии, указанной в пути `sessionId` — если нет, это
  `409` (а не `404`/`403`), потому что сам вопрос существует и доступен, просто запрос обратился
  не к той сессии.
- **Завершение требует ответа на ВСЕ основные вопросы — досрочного финиша нет.** В отличие от
  тренажёра, здесь нет порога «минимум N ответов»: `finish` сравнивает число отвеченных основных
  вопросов с `totalQuestions` и при любом расхождении отвечает `409`. Уточняющие вопросы в этот
  подсчёт не входят.
- **Оценивание в отчёте идёт кейсами, а не по каждому вопросу.** Кейс — это основной вопрос и все
  отвеченные уточнения к нему. LLM разбирает кейс целиком и выставляет одну оценку (`score`,
  1-5) и один текстовый разбор сразу на ответ на основной вопрос и на ответы на все его
  уточнения — по отдельности они не оцениваются. Оценка и разбор попадают в поля
  `score`/`feedback` основного вопроса кейса.
- **Уточняющие вопросы эфемерны.** При `finish` они удаляются из БД вместе с любыми оставшимися
  неотвеченными вопросами (в штатном сценарии это могут быть только уточнения — основные к этому
  моменту гарантированно все отвечены, иначе `finish` не прошёл бы) — сразу после того, как их
  содержимое учтено в оценке кейса. Поэтому `questions` в отчёте (и в `finish`, и в
  `GET .../report`) состоит только из основных вопросов; текстов уточнений и ответов на них в
  отчёте нет.
- **Плохой отчёт не сохраняется.** Если LLM не дала внятный итоговый фидбэк (короче 10 символов),
  не вернула распознаваемую вероятность оффера или оценила меньше половины кейсов, `finish`
  отвечает `503`, а сессия остаётся незавершённой — запрос можно повторить, LLM отработает
  заново. Отдельные невалидные оценки (индекс вне диапазона, балл вне 1-5, пустой разбор, дубль
  на тот же кейс) отбрасываются: такой кейс останется в отчёте без `score`/`feedback`, если порог
  в половину кейсов при этом выдержан.
- **Средний балл считается на бэке**, а не берётся из LLM целиком: это среднее по оценкам только
  тех кейсов, которые LLM реально оценила (по одной оценке на кейс, независимо от числа
  уточнений внутри него), округлённое до одного знака после запятой.
- **`recommendations` — мягкое поле, может отсутствовать.** Пустая или пробельная строка от LLM
  превращается в `null` на бэке, колонка в БД nullable — отчёт без рекомендаций не считается
  невалидным и не блокирует `finish`. На момент написания разбор этого поля в тексте промпта
  подробно описан только у junior-агента ревью; у остальных грейдов (noexp/middle/senior) поле
  предусмотрено схемой ответа, но насколько надёжно оно заполняется — зависит от калибровки
  конкретного агента. Так что `null` в `recommendations` не всегда означает «рекомендовать
  нечего» — может быть, что агент этого грейда пока просто не считает нужным его заполнять.
- **Сессия завершается один раз.** После `finish` статус — `COMPLETED`, проставляется
  `completedAt`. Повторный `finish` на уже завершённой сессии — `409`, отчёт не пересобирается;
  посмотреть его повторно можно только через `GET .../report`. Два параллельных `finish` тоже
  дадут ровно один отчёт: проигравший запрос получит `409`.
- **`answeredCount`** в `InterviewSessionResponse` считает только отвеченные основные вопросы
  (уточняющие не входят), даже если по факту в сессии есть отвеченные уточнения.
- **Удаление** — физическое: сессия удаляется вместе со всеми вопросами, ответами и отчётом (не
  soft delete).

## Вспомогательные ручки вакансий — `/api/v1/vacancies`

Отдельный контроллер того же домена `vacancy`, что обслуживает интервью данными о вакансиях hh.ru.
Обе ручки требуют того же access-токена, что и `/api/v1/interview/**` (тот же
`SecurityConfig`, отдельного `permitAll` для `/api/v1/vacancies/**` нет).

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| GET | `/preview` | предпросмотр вакансии по ссылке перед созданием сессии | cookie `access_token` |
| GET | `/status` | живой статус вакансии на hh.ru (активна/в архиве/удалена) | cookie `access_token` |

```java
record VacancyPreviewResponse(String name, String employer, String salary, String experience, String url)

record VacancyStatusResponse(Status status) // enum Status { ACTIVE, ARCHIVED, NOT_FOUND }
```

- **`GET /preview?url=`** — `200` с краткой сводкой по вакансии: название, работодатель, зарплата
  (строкой, может отсутствовать — `null`) и требуемый опыт. Полезно перед `POST
  /api/v1/interview/sessions`, чтобы показать пользователю, по какой вакансии он собирается
  проходить интервью, не тратя вызов LLM. `url` разбирается тем же паттерном hh.ru-ссылки, что и
  `vacancyUrl` в интервью; вакансия не найдена или в архиве — `404`; hh.ru недоступен — `503`.
- **`GET /status?url=`** — `200` с одним из трёх статусов: `ACTIVE`, `ARCHIVED` (снята с
  публикации, но существует) или `NOT_FOUND` (hh.ru вернул 404 — это не ошибка запроса, а
  валидный статус). Результат кешируется на сервере in-memory по id вакансии на **30 минут**
  (`STATUS_TTL`) без вытеснения — повторные проверки одной и той же вакансии в этом окне не
  дёргают hh.ru заново. hh.ru недоступен (не 404, а реальная сетевая/серверная ошибка) — `503`,
  в кеш такой результат не попадает.

Обе ручки не создают и не изменяют сессий интервью и снапшотов вакансий — это чисто читающие
операции для UI (предпросмотр перед стартом и проверка «жива ли ещё вакансия» у уже созданной
сессии).

Пример `VacancyPreviewResponse`:

```json
{
  "name": "Java-разработчик",
  "employer": "ООО Ромашка",
  "salary": "150 000 - 250 000 ₽",
  "experience": "От 1 года до 3 лет",
  "url": "https://hh.ru/vacancy/123456"
}
```

Пример `VacancyStatusResponse`:

```json
{
  "status": "ARCHIVED"
}
```

## Ошибки

Тело ошибки — стандартный `ApiError`:

```json
{
  "timestamp": "2026-07-28T12:00:00",
  "status": "CONFLICT",
  "message": "Conflict.",
  "errors": ["Not all questions answered"]
}
```

| Код | Когда |
|---|---|
| `400` | невалидное тело запроса (пустой `vacancyUrl`/`answerText`, битый JSON), `vacancyUrl`/`url` не содержит распознаваемую ссылку на вакансию hh.ru, неверный тип path-параметра (`sessionId`/`questionId` не UUID) |
| `401` | нет валидного access-токена (ставит Security-фильтр, тело пустое) |
| `403` | вопрос, на который отправляется ответ, принадлежит другому пользователю |
| `404` | сессия, вопрос или отчёт не найдены (в т.ч. чужие — сессии ищутся сразу с учётом пользователя); вакансия по ссылке не найдена или в архиве (`POST /sessions`, `GET /vacancies/preview`) |
| `409` | сессия уже завершена (в т.ч. если её завершил параллельный запрос); неотвеченных вопросов не осталось (`.../questions/next`); вопрос уже отвечен; вопрос не принадлежит указанной в пути сессии; при `finish` — отвечены не все основные вопросы |
| `503` | hh.ru недоступен (`POST /sessions`, `GET /vacancies/preview`, `GET /vacancies/status`); AI-сервис недоступен или вернул непригодный ответ — при создании сессии (LLM дала меньше 5 пригодных вопросов), при `.../questions/next` (только если сам вызов LLM за решением об уточнении сорвался — пустое или отрицательное решение ошибкой не считается), при `finish` (пустой/слишком короткий итоговый фидбэк, нераспознанная вероятность оффера либо оценено меньше половины кейсов) |

`503` от AI-сервиса и от hh.ru различаются сообщением в `ApiError` (`"AI service unavailable."`
и `"Vacancy service unavailable."` соответственно), но кодом и структурой тела — нет.
