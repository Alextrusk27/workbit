# Interview API — `/api/v1/interview`

AI-интервью по конкретной вакансии hh.ru: пользователь присылает ссылку на вакансию, бэкенд
подтягивает её данные с hh.ru, и модель-интервьюер ведёт по ней живую адаптивную беседу — как на
реальном собеседовании. При создании сессии модель составляет план (сколько основных вопросов
задать и какие темы закрыть под эту вакансию — с учётом названия, работодателя, ключевых
навыков, описания и требуемого опыта) и формулирует первый вопрос; каждый следующий вопрос
рождается уже по ходу беседы — модель видит вакансию, план и всю историю «вопрос — ответ» и
решает, что сказать дальше: задать следующий основной вопрос, развить текущий уточнением,
переспросить, если вопрос не поняли, или вернуть кандидата к вопросу, если ответ был не по теме.
Завершить интервью можно только ответив на **все** основные вопросы — в отличие от тренажёра
(`docs/training-api.md`), досрочного финиша по инициативе пользователя здесь нет (у самой беседы
есть одно исключение — см. «Поведение»). При завершении отдельный агент-ревьюер разбирает все
ответы (с учётом уточнений) кейсами и формирует отчёт: оценку по каждому основному вопросу,
средний балл, оценку вероятности оффера и рекомендации, что проработать перед реальным
собеседованием. Все тела запросов и ответов — JSON.

Домен во многом зеркалит тренажёр (сессия → вопросы по одному → уточнения → отчёт), но не
разделяет с ним ни данные, ни правила: здесь нет навыка и профессии, вопросы не берутся из банка,
а рождаются по ходу беседы под конкретную вакансию, и порог для завершения — не «минимум N
ответов», а «отвечены все».

Кроме работы с отдельной сессией, домен даёт агрегированный взгляд по вакансии в целом — сколько
раз по ней уже проходили интервью, какой лучший результат и что стоит подтянуть перед следующей
попыткой; см. «Агрегация по вакансиям» ниже.

## Доступ

Домен закрыт целиком: `SecurityConfig` требует аутентификации на любой путь, не входящий
в `/api/v1/auth/**` и Swagger. Ко всем ручкам `/api/v1/interview/**` (и, отдельно, к ручкам
вакансий `/api/v1/vacancies/**` — см. ниже) нужен валидный access-токен — cookie `access_token`
(для Swagger в dev поддержан fallback `Authorization: Bearer <accessToken>`). Без него — `401`
с пустым телом (это делает Security-фильтр, а не контроллер, поэтому тело `ApiError` не
приходит).

Сессии и вопросы привязаны к пользователю из токена. Большинство ручек (получение сессии,
следующий вопрос, завершение, отчёт, отзыв на отчёт) сами ищут ресурс с учётом `userId`,
поэтому чужой ресурс для них просто «не существует» — ответ `404`. Исключение — отправка ответа
(`POST .../questions/{questionId}`) и отзыв на вопрос
(`POST .../questions/{questionId}/feedback`): в обеих ручках вопрос сначала ищется по
`questionId` без учёта владельца, и если он оказывается чужим, это разбирается явно — ответ
`403`. Ручки агрегации по вакансиям (`GET`/`DELETE /vacancies/{vacancyId}`) следуют общему
правилу — ищут интервью сразу с учётом `userId`, поэтому вакансия, по которой у текущего
пользователя нет интервью, — тоже `404`, даже если по ней есть интервью у другого пользователя.

## Эндпоинты

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| POST | `/sessions` | создать сессию интервью по ссылке на вакансию | cookie `access_token` |
| GET | `/sessions/{sessionId}` | получить сессию по id | cookie `access_token` |
| GET | `/sessions/{sessionId}/questions` | история: отвеченные вопросы сессии вместе с ответами | cookie `access_token` |
| POST | `/sessions/{sessionId}/questions/next` | получить текущий неотвеченный вопрос (основной или уточняющий) | cookie `access_token` |
| POST | `/sessions/{sessionId}/questions/{questionId}` | отправить ответ на вопрос | cookie `access_token` |
| POST | `/sessions/{sessionId}/questions/{questionId}/feedback` | оценить разбор вопроса (лайк/дизлайк) | cookie `access_token` |
| POST | `/sessions/{sessionId}/report/feedback` | оценить итоговый отчёт (лайк/дизлайк) | cookie `access_token` |
| POST | `/sessions/{sessionId}/finish` | завершить интервью и сформировать отчёт | cookie `access_token` |
| GET | `/sessions/{sessionId}/report` | получить ранее сформированный отчёт | cookie `access_token` |

## Справочные значения

- **`InterviewSession.Status`** — `CREATED`, `IN_PROGRESS`, `COMPLETED`. Кастомного лейбла нет,
  сериализуется по имени константы (как `TrainingSession.Status`).
- **`InterviewReport.OfferProbability`** — сериализуется не по имени, а по русскому лейблу через
  `@JsonValue`: `LOW` → `"Низкая"`, `MEDIUM` → `"Средняя"`, `HIGH` → `"Высокая"`. Приходит только
  в отчёте, в запросах этого поля нет.

## Запросы (DTO)

```java
record CreateInterviewSessionRequest(@NotBlank String vacancyUrl)

record SubmitAnswerBody(@NotBlank String answerText)

record FeedbackRequest(
    @NotNull InterviewUserFeedback.Vote vote,
    @NotNull @Size(max = 10) List<@Size(max = 100) String> reasons,
    @Size(max = 2000) String comment)
```

`vacancyUrl` — ссылка на вакансию hh.ru; из неё регулярным выражением вычленяется числовой id
вакансии (`hh\.ru/vacancy/(\d+)`, поиск подстроки, а не сверка со всей строкой). Поддомены вида
`spb.hh.ru`, `hh.kz` и т.п. проходят так же, как `hh.ru`, лишь бы в строке нашлась эта подстрока;
протокол (`http`/`https`) не проверяется. Ссылка, не подходящая под этот паттерн, — `400`. Сама
вакансия при этом валидируется отдельно: если по вычлененному id hh.ru вернул 404 или пометил
вакансию архивной — `404`, а не `400` (ссылка синтаксически валидна, но вакансии недоступны).

`FeedbackRequest` — тело обеих ручек отзыва (на вопрос и на отчёт), одинаковое для обеих.
`vote` — `UP` (лайк) или `DOWN` (дизлайк), обязателен. `reasons` — список причин дизлайка, до 10
строк не длиннее 100 символов каждая; поле обязательно как таковое (пустой массив `[]`, а не
отсутствующее поле) — у лайка ожидается пустым по соглашению фронта, но бэк это не
перепроверяет и непустой `reasons` при `vote: "UP"` не отклонит. `comment` — необязательный
свободный текст до 2000 символов.

`POST .../questions/next`, `POST .../finish` и `GET .../report` тела не принимают.

Пример `CreateInterviewSessionRequest`:

```json
{
  "vacancyUrl": "https://hh.ru/vacancy/123456"
}
```

Пример `FeedbackRequest` (дизлайк):

```json
{
  "vote": "DOWN",
  "reasons": ["Оценка занижена"],
  "comment": "Разбор не заметил вторую часть ответа"
}
```

## Ответы

```java
record InterviewSessionResponse(
    UUID id, String vacancyId, String vacancyName, String employer, String vacancyUrl,
    String experience, InterviewSession.Status status, int answeredCount, int totalQuestions,
    Instant created, Instant completedAt, String closingRemark)

record InterviewQuestionResponse(
    UUID questionId, int orderIndex, String questionText, boolean followUp,
    String answerText, Integer score, String feedback)

record InterviewReportResponse(
    UUID reportId, UUID sessionId, Double avgScore, InterviewReport.OfferProbability offerProbability,
    String overallFeedback, String recommendations, String weakestSkill, Instant generatedAt,
    List<InterviewQuestionResponse> questions)
```

- **`POST /sessions`** — `201` с `InterviewSessionResponse` и заголовком `Location`
  (`/sessions/{id}`). Свежесозданная сессия: `status = CREATED`, `answeredCount = 0`,
  `totalQuestions` — число основных вопросов из плана, который составила модель (от 5 до 12, см.
  «Поведение»); дальше по ходу беседы оно, как правило, не меняется, но в редком случае
  досрочного завершения беседы может уменьшиться (см. «Поведение»). `vacancyName`/`employer`/
  `vacancyUrl`/`experience` берутся из только что сохранённого снапшота вакансии; `vacancyUrl` в
  ответе — всегда канонический вид `https://hh.ru/vacancy/{id}`, даже если в запросе была ссылка
  на поддомен или с лишними query-параметрами. `experience` — как есть в вакансии hh.ru
  (например, «От 1 года до 3 лет»), `null`, если в вакансии не указан. `vacancyId` — тот же
  идентификатор вакансии, что в ручках `/vacancies` ниже (числовой id вакансии на hh.ru строкой):
  по нему фронт ведёт со страницы прогона на страницу вакансии. Список вопросов в ответе нет —
  готов только первый вопрос беседы; дальше вопросы рождаются на бэке по ходу разговора и
  отдаются по одному через `.../questions/next`.
- **`GET /sessions/{sessionId}`** — `200`, `InterviewSessionResponse` с актуальным
  `answeredCount`. `closingRemark` заполнен, только если интервьюер оборвал беседу сам, — там
  лежит его прощальная реплика (см. «Поведение»); в остальных случаях `null`.
- **`GET .../questions`** — `200`, массив `InterviewQuestionResponse` с уже отвеченными
  вопросами сессии и текстами ответов в поле `answerText`. Порядок — как шла беседа: основной
  вопрос, следом все его уточнения в порядке беседы, затем следующий основной; уточнений у
  одного основного вопроса может быть несколько (развитие темы — не больше одного, переспросов
  и возвратов к теме — сколько потребовалось, см. «Поведение»). Неотвеченные вопросы в список не
  попадают — текущий по-прежнему берётся через `.../questions/next`. `score`/`feedback` до
  завершения интервью `null`. Ручка нужна фронту, чтобы при возврате в незавершённое интервью
  показать всю переписку, а не только текущий вопрос. Работает и после завершения интервью:
  уточнения с ответами из базы не удаляются, поэтому по завершённой сессии ручка отдаёт полную
  беседу — в отличие от отчёта, где остаются только основные вопросы.
- **`POST .../questions/next`** — `200`, `InterviewQuestionResponse`. Если есть уже заданный, но
  неотвеченный вопрос — возвращает его. Иначе просит модель продолжить беседу по последнему
  ответу и превращает её реплику в вопрос: новый основной либо уточнение (развитие темы,
  переспрос или возврат к теме — все три показываются с `followUp: true`, различить их по DTO
  нельзя, только по тексту вопроса). Если основных задано столько, сколько в плане, — беседа
  закончена, ручка отвечает `409` (см. «Поведение»); тем же `409` заканчивается беседа, которую
  оборвал сам интервьюер, — его прощальную реплику фронт берёт из `closingRemark` сессии. `answerText`, `score`, `feedback` для
  только что полученного вопроса всегда `null` — по ходу интервью оценок нет.
- **`POST .../questions/{questionId}`** — `204`, пустое тело. Фидбэка в ответе нет — оценка
  появится только в отчёте после `finish`.

  `score`/`feedback` в `InterviewQuestionResponse` относятся не к отдельному вопросу, а к кейсу
  целиком (основной вопрос + его уточнения — см. «Поведение»): после `finish` они заполняются у
  основного вопроса кейса и описывают разбор всего кейса, включая ответы на уточнения. Сами
  уточняющие вопросы в отчёт не попадают, поэтому `InterviewReportResponse.questions` состоит
  только из основных вопросов (`followUp: false` у каждого элемента); их тексты и ответы на них
  никуда не деваются — они остаются в базе и доступны через `GET .../questions` (см.
  «Поведение»).
- **`POST .../questions/{questionId}/feedback`**, **`POST .../report/feedback`** — `204`,
  пустое тело у обеих. Отзыв нигде обратно не отдаётся — ни в ответе самой ручки, ни в отчёте,
  ни где-либо ещё в контракте (см. «Поведение»).
- **`POST .../finish`** — `201` с `InterviewReportResponse` и заголовком `Location`
  (`/sessions/{id}/report`).
- **`GET .../report`** — `200`, `InterviewReportResponse`.

Пример `InterviewSessionResponse` (свежесозданная сессия):

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "vacancyId": "123456",
  "vacancyName": "Java-разработчик",
  "employer": "ООО Ромашка",
  "vacancyUrl": "https://hh.ru/vacancy/123456",
  "experience": "От 1 года до 3 лет",
  "status": "CREATED",
  "answeredCount": 0,
  "totalQuestions": 12,
  "created": "2026-07-28T10:00:00Z",
  "completedAt": null,
  "closingRemark": null
}
```

Прогресс «5/10» на фронте — это `answeredCount`/`totalQuestions`; уточняющие вопросы в оба поля
не входят.

Пример `InterviewQuestionResponse` (неотвеченный уточняющий вопрос):

```json

  "orderIndex": 1,

  "answerText": null,

  "feedback": null
}
```

Пример `InterviewReportResponse`:

  "avgScore": 3.8,

Как и в тренажёре, первый вопрос выше — целый кейс (основной вопрос + оценённое уточнение про

успела оценить: `score`/`feedback` тогда остаются `null` даже в уже сформированном отчёте. Это
допустимо, пока в целом оценена как минимум половина кейсов — иначе `finish` завершится `503`
(см. «Ошибки»).

## Поведение

- **Создание сессии синхронно с составлением плана и первого вопроса.** `POST /sessions` тремя
  шагами: забирает данные вакансии с hh.ru (`VacancyService.fetch`), одним вызовом модели
  получает план собеседования — сколько основных вопросов задать (число выбирает модель, код
  лишь обрезает его в коридор 5..12) и какие темы закрыть — вместе с текстом первого вопроса, и
  сохраняет неизменный снапшот вакансии, сессию и этот единственный вопрос. Если план пришёл без
  первого вопроса, бэкенд один раз переспрашивает модель, а если и это не помогло — отвечает
  `503`, сессия в этом случае не создаётся вовсе. Всё это — один HTTP-запрос; ответ приходит
  только когда план и первый вопрос уже готовы, отдельного «прогресса генерации» нет. Остальные
  вопросы этим вызовом не готовятся — каждый следующий запрашивается у модели отдельно, по ходу
  беседы (см. ниже).
- **Нельзя параллельно вести два незавершённых интервью по одной вакансии.** Сразу после
  загрузки вакансии с hh.ru и до вызова LLM (чтобы не тратить платный вызов впустую) бэкенд
  проверяет по `source_id` вакансии, есть ли у текущего пользователя интервью в статусе
  `CREATED` или `IN_PROGRESS` по любому из снапшотов с этим же `source_id` — снапшотов у одной
  вакансии может быть несколько (см. «Агрегация по вакансиям»), проверка учитывает их все. Если
  такое интервью уже есть — `409` с деталью `Unfinished interview exists`, план для вакансии не
  запрашивается. Ограничение действует per-vacancy: по другим вакансиям создавать интервью можно
  без оглядки на то, что где-то ещё есть незавершённая попытка. На фронте это ожидаемый конфликт,
  а не ошибка: увидев `409`, вместо создания новой сессии предлагают «Продолжить интервью» —
  открыть уже существующую незавершённую.
- **Создание сессии расходует квоту интервью.** Сразу за проверкой на незавершённое интервью, но
  до вызова LLM, бэкенд проверяет остаток интервью по тарифу — если он исчерпан,
  `402` с деталью `Interview quota exhausted`, план не запрашивается. Настоящее списание —
  атомарное, происходит позже, уже в транзакции, которая сохраняет сессию; подробности механики
  квот и коды тарифа — в `docs/billing-api.md`.
- **Вакансия сохраняется как неизменный снапшот на момент создания сессии.** Данные о вакансии
  внутри уже созданной сессии не обновляются, даже если объявление на hh.ru потом изменится или
  будет снято с публикации. Чтобы узнать актуальный статус вакансии прямо сейчас — отдельная
  ручка `GET /api/v1/vacancies/status` (см. ниже), она саму сессию никак не трогает.
- **Саму беседу от начала до конца ведёт один агент, без разделения по опыту.** Модель получает
  требуемый вакансией опыт как часть снапшота вакансии (строкой — «Нет опыта», «От 1 года до
  3 лет» и т. п.) и сама выбирает по нему уместную планку сложности; отдельных версий агента под
  разные категории опыта для составления плана, первого вопроса и последующих реплик здесь нет —
  в отличие от тренажёра, где сложность настраивают через выбор LLM-агента. Деление по опыту
  сохранилось только у итогового ревью: как и раньше, `finish` отдаёт ответы одному из четырёх
  агентов-ревьюеров — exp0/exp1/exp3/exp6, по той же биекции с категорией опыта hh.ru («Нет
  опыта» → exp0, «От 1 года до 3 лет» → exp1, «От 3 до 6 лет» → exp3, «Более 6 лет» → exp6,
  любой не распознанный или отсутствующий вариант — exp1): оценивать ответ на «расскажите про
  индексы» разумно по-разному в зависимости от опыта кандидата, а вести саму беседу — нет.
- **Количество основных вопросов выбирает модель, в границах коридора.** При составлении плана
  модель сама решает, сколько основных вопросов задать под эту вакансию; код лишь обрезает её
  число в коридор от 5 до 12. `totalQuestions` фиксируется в момент создания сессии и в норме
  дальше не меняется — но в редком случае досрочного завершения беседы (интервьюер оборвал
  разговор, см. ниже) подрезается до фактически отвеченных основных вопросов, потому что иначе
  `finish` требовал бы ответов на вопросы, которых уже не будет. Раз фронт считает прогресс
  «N / totalQuestions», это стоит учитывать: число в знаменателе способно уменьшиться по ходу
  интервью.
- **`.../questions/next` идемпотентен.** Пока последний заданный вопрос не отвечен — будь то
  основной или любое из уточнений — ручка возвращает его как есть, не обращаясь к модели
  повторно. Это и точка возврата: прервал интервью и вернулся — повторный вызов даст тот же
  вопрос, на который ещё нет ответа.
- **История незавершённого интервью доступна, оценок в ней нет.** Уже отвеченные вопросы вместе
  с ответами отдаёт `GET .../questions` — по ней фронт восстанавливает переписку, когда
  пользователь вернулся в прерванное интервью. Промежуточных оценок в этой истории нет:
  `score`/`feedback` заполняются только после `finish`, полный разбор — через ответ `finish`
  или `GET .../report`.
- **Как рождается очередной вопрос.** После каждого ответа, если он ещё не разобран, бэкенд
  **ровно один раз** обращается к модели за следующей репликой; решение (любое) фиксирует тот же
  флаг в БД, что раньше закрывал только уточнение (`follow_up_checked`) — теперь он означает
  «по этому ответу модель уже сходила». Поэтому повторные вызовы `next` (например, после
  перезагрузки страницы) не приводят ни к повторному платному обращению к модели, ни к тому, что
  она «передумает» и подсунет второй вопрос по тому же ответу. Контекст запроса — не текущий
  кейс, а вся беседа целиком: снапшот вакансии (название, работодатель, требуемый опыт, ключевые
  навыки, описание), план и полная история «вопрос — ответ» с начала интервью.
- **Реплика модели — один из пяти видов**, и что с ней делать в итоге, решает код:
  - новый основной вопрос — просто следующий вопрос по плану;
  - уточнение к текущему основному (развитие темы) — не больше одного на основной вопрос: если
    к этому основному уточнение такого рода уже задавалось, повторное решение модели того же
    вида код трактует как новый основной вопрос;
  - пояснение непонятого вопроса и переспрос — таких за один основной вопрос может быть сколько
    угодно, лимита нет;
  - возврат кандидата к вопросу, если ответ был не по теме (в том числе просьба оценить ответ
    прямо сейчас) — таких тоже может быть сколько угодно;
  - обрыв беседы — решает сама модель: кандидат попросил закончить, третий раз подряд уходит от
    вопроса или перешёл на оскорбления. Вопрос при этом не сохраняется, `next` отвечает `409`, а
    прощальная реплика интервьюера ложится в `closingRemark` сессии — фронт показывает её перед
    разбором. Со стороны кода остаётся только страховка от топтания на одном вопросе: как только
    у одного основного вопроса набралось шесть реплик, опрос закрывается, к модели за очередной
    репликой уже не идут.

  Пользователю уточнение, переспрос и возврат показываются одинаково, как уточняющий вопрос
  (`followUp: true`) — различить их по DTO нельзя, только по тексту; в `totalQuestions` и
  `answeredCount` они не входят.
- **Гонки и повторные вызовы.** Тот же флаг `follow_up_checked` гасит и запоздалый ответ модели:
  если запрос `next` оборвался у клиента (или пользователь перезагрузил страницу) и решение по
  ответу за это время принял другой запрос, вернувшийся результат отбрасывается — второй вопрос
  по тому же ответу не сохраняется. Дополнительно это гарантирует БД: пара (кейс, `order_index`)
  уникальна, поэтому конкурентная запись второй реплики к тому же ответу упадёт на уникальном
  индексе, а не создаст дубль. Вырожденный ответ модели (пустой текст вопроса) получает один
  повторный вызов и затем `503`, кроме одного легитимного случая — пустой текст у нового
  основного вопроса ровно тогда, когда основных уже задано столько, сколько в плане: это сигнал
  конца беседы, а не сбой.
- **`orderIndex` считается по-разному** у основных и уточняющих: у основного — номер вопроса в
  сессии (1..N), у уточняющего — номер внутри своего кейса (1, 2, 3... по числу переспросов и
  уточнений у этого основного вопроса). Сквозной нумерации по сессии у уточнений нет, и у разных
  кейсов `orderIndex` уточнений может совпадать — их различает принадлежность к разным основным
  вопросам, а не порядковый номер.
- **Оценок по ходу интервью нет.** `POST .../questions/{questionId}` только сохраняет текст
  ответа и отвечает `204` без `score`/`feedback`. Весь фидбэк формируется одним пакетом при
  завершении. Повторно ответить на уже отвеченный вопрос нельзя — `409`. Как только сохранён
  первый ответ, статус сессии переходит из `CREATED` в `IN_PROGRESS`.
- **Проверка принадлежности вопроса.** Помимо владельца, у отправки ответа и у отзыва на вопрос
  проверяется, что `questionId` действительно относится к сессии, указанной в пути `sessionId` —
  если нет, это `409` (а не `404`/`403`), потому что сам вопрос существует и доступен, просто
  запрос обратился не к той сессии.
- **Отзыв на разбор — append-only и ни на что не влияет.** Обе ручки (`.../feedback` у вопроса
  и у отчёта) просто добавляют строку в `interview.user_feedback` (`question_id = NULL` у отзыва
  на отчёт) и ничего не читают и не пересчитывают в ответ — это сырьё для ручного улучшения
  вопросов и промптов разборов, а не часть продуктового контракта: ни на балл, ни на текст
  фидбэка, ни на что-либо ещё в отчёте отзыв не влияет. Отзыв не отдаётся обратно ни в одном
  ответе API — читать свой прошлый отзыв через API нельзя. В отличие от отправки ответа, отзыв
  на вопрос не требует, чтобы вопрос уже был отвечен, и не проверяет статус сессии — оставить
  отзыв можно и на уточняющий вопрос, пока он физически существует в БД (при `finish` удаляются
  неотвеченные вопросы — в штатном сценарии это может быть только висящее уточнение, — отзыв на
  такой вопрос после этого момента отвечает `404`; отвеченные уточнения остаются, и отзыв на них
  работает и после завершения, см. «Уточнения хранятся вместе с ответами» ниже). Отзыв на отчёт требует, чтобы отчёт
  уже существовал — `finish` ещё не вызывался или сессия не найдена — `404`. Отдельного удаления
  сессии в этом домене нет — единственный способ стереть отзывы вместе с интервью,
  `DELETE /vacancies/{vacancyId}`, каскадом удаляет и строки `interview.user_feedback` этой
  вакансии.
- **Завершение требует ответа на ВСЕ основные вопросы плана — но иногда беседу заканчивает код,
  а не пользователь.** `finish` сравнивает число отвеченных основных вопросов с `totalQuestions`
  и при любом расхождении отвечает `409` — специального порога «минимум N ответов», как в
  тренажёре, здесь нет. Но сам `totalQuestions` не всегда равен числу из исходного плана: если
  беседа завершилась досрочно из-за третьего возврата к теме (см. выше), бэкенд подрезает его до
  фактически отвеченных основных вопросов, поэтому `finish` в этом случае проходит сразу, без
  дополнительных вопросов. Уточняющие вопросы в подсчёт отвеченных основных не входят в любом
  случае.
- **Оценивание в отчёте идёт кейсами, а не по каждому вопросу.** Кейс — это основной вопрос и все
  отвеченные уточнения к нему. LLM разбирает кейс целиком и выставляет одну оценку (`score`,
  1-5) и один текстовый разбор сразу на ответ на основной вопрос и на ответы на все его
  уточнения — по отдельности они не оцениваются. Оценка и разбор попадают в поля
  `score`/`feedback` основного вопроса кейса.
- **Уточнения хранятся вместе с ответами.** Уточняющий вопрос и ответ на него остаются в базе
  и после завершения интервью — их отдаёт `GET .../questions` (история беседы целиком). При
  `finish` удаляются только неотвеченные вопросы: в штатном сценарии это разве что уточнение,
  заданное последним и оставленное без ответа (основные к этому моменту гарантированно все
  отвечены, иначе `finish` не прошёл бы). В отчёте уточнений по-прежнему нет: `questions` и в
  ответе `finish`, и в `GET .../report` состоит только из основных вопросов — содержимое
  уточнений учтено в оценке и разборе своего кейса.
- **Плохой отчёт не сохраняется.** Если LLM не дала внятный итоговый фидбэк (короче 10 символов),
  не вернула распознаваемую вероятность оффера или оценила меньше половины кейсов, `finish`
  отвечает `503`, а сессия остаётся незавершённой — запрос можно повторить, LLM отработает
  заново. Отдельные невалидные оценки (индекс вне диапазона, балл вне 1-5, пустой разбор, дубль
  на тот же кейс) отбрасываются: такой кейс останется в отчёте без `score`/`feedback`, если порог
  в половину кейсов при этом выдержан.
- **Средний балл считается на бэке**, а не берётся из LLM целиком: это среднее по оценкам только
  тех кейсов, которые LLM реально оценила (по одной оценке на кейс, независимо от числа
  уточнений внутри него), округлённое до одного знака после запятой.
- **`recommendations` — мягкое поле, может отсутствовать.** Пустая или пробельная строка от LLM
  превращается в `null` на бэке, колонка в БД nullable — отчёт без рекомендаций не считается
  невалидным и не блокирует `finish`. Поле описано в текстах всех четырёх агентов ревью, но
  насколько надёжно оно заполняется — зависит от калибровки конкретного агента. Так что `null`
  в `recommendations` не всегда означает «рекомендовать нечего» — может быть, что агент этой
  категории опыта просто не стал его заполнять.
- **`weakestSkill` — самый слабый навык по итогам интервью, тоже мягкое поле.** Ревьюер называет
  тему или навык из требований вакансии, раскрытую в ответах слабее всего, коротким названием
  (1–3 слова, как в справочнике навыков тренажёра) — по нему клиент предлагает точечную
  тренировку. Пустая или пробельная строка превращается в `null`; слишком длинный ответ LLM
  (больше 100 символов, столько же в колонке) тоже отбрасывается в `null` — отчёт из-за этого
  поля не падает и `finish` не блокирует. Поле описано в тексте всех четырёх грейдовых
  ревьюеров, но гарантии заполнения нет: `null` возможен, и клиенту нужно уметь обходиться
  без него.
- **Сессия завершается один раз.** После `finish` статус — `COMPLETED`, проставляется
  `completedAt`. Повторный `finish` на уже завершённой сессии — `409`, отчёт не пересобирается;
  посмотреть его повторно можно только через `GET .../report`. Два параллельных `finish` тоже
  дадут ровно один отчёт: проигравший запрос получит `409`.
- **`answeredCount`** в `InterviewSessionResponse` считает только отвеченные основные вопросы
  (уточняющие не входят), даже если по факту в сессии есть отвеченные уточнения.
- **Удаление** — физическое и только целиком по вакансии (`DELETE /vacancies/{vacancyId}`, см.
  ниже): сессии удаляются вместе со всеми вопросами, ответами и отчётами (не soft delete).
  Ручки удаления отдельной сессии нет.

## Агрегация по вакансиям — `/api/v1/interview/vacancies`

Тот же контроллер и тот же домен, что и сессии выше (не отдельный поддомен, в отличие от
`/api/v1/vacancies` ниже) — просто другой срез тех же данных: не отдельная сессия, а сводка по
вакансии в целом. Группировка нужна, чтобы показать пользователю страницу вакансии — сколько раз
он проходил по ней интервью, какой лучший результат и что стоит подтянуть перед следующей
попыткой — не вытягивая и не сопоставляя все сессии на фронте.

### Эндпоинты

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| GET | `/vacancies` | список вакансий пользователя со сводкой по интервью | cookie `access_token` |
| GET | `/vacancies/{vacancyId}` | детали вакансии: все интервью по ней и рекомендованные тренировки | cookie `access_token` |
| DELETE | `/vacancies/{vacancyId}` | удалить все интервью пользователя по вакансии | cookie `access_token` |

`vacancyId` в пути — не UUID сессии и не UUID снапшота, а тот же числовой id вакансии на hh.ru,
что виден в `vacancyUrl` (`https://hh.ru/vacancy/{vacancyId}`), просто строкой, без проверки
формата. Несуществующий или ни на что не похожий `vacancyId` — тоже `404` (не `400`, как было бы
у `sessionId`/`questionId` при невалидном UUID): путь не парсится как UUID, проверяется только
«есть ли у пользователя интервью с таким id вакансии».

### DTO ответов

```java
record InterviewVacancyResponse(
    String vacancyId, String vacancyName, String employer, String vacancyUrl, String experience,
    InterviewSession.Status status, int completedCount, Double bestScore,
    InterviewReport.OfferProbability bestOffer, Instant lastActivity)

record InterviewVacancyDetailResponse(
    String vacancyId, String vacancyName, String employer, String vacancyUrl, String experience,
    List<InterviewAttemptResponse> interviews, List<RecommendedTrainingResponse> recommendedTrainings)

record InterviewAttemptResponse(
    UUID sessionId, InterviewSession.Status status, Instant created, Instant completedAt,
    Double avgScore, InterviewReport.OfferProbability offerProbability)

record RecommendedTrainingResponse(
    String skill, Double interviewScore, UUID trainingSessionId, String trainingStatus,
    Double trainingScore, Integer answeredCount, Integer totalQuestions)
```

`offerProbability`/`bestOffer` сериализуются тем же способом, что и в отчёте интервью
(`@JsonValue`, русский лейбл: «Низкая»/«Средняя»/«Высокая», см. «Справочные значения» выше).

`trainingStatus` — статус тренировки-тренажёра (`CREATED`/`IN_PROGRESS`/`COMPLETED`), но, в
отличие от `status` в `InterviewVacancyResponse`/`InterviewAttemptResponse`, на бэке это обычная
строка, а не enum — разница видна только в OpenAPI-схеме (там она с `allowableValues`), по
значениям и по JSON на проводе отличий нет.

### Ответы

- **`GET /vacancies`** — `200`, `List<InterviewVacancyResponse>` — все вакансии, по которым у
  пользователя есть хотя бы одно интервью, каждая одной строкой сводки; если интервью нет вовсе —
  пустой список, а не ошибка. Порядок: вакансия с самым недавно СОЗДАННЫМ интервью — первая
  (сортировка по `created` интервью, а не по `completedAt` и не по последнему действию
  пользователя внутри интервью).
  - `status`, `vacancyName`/`employer`/`vacancyUrl`/`experience` — от самого недавнего по
    `created` интервью по этой вакансии, даже если оно ещё не завершено. Если у вакансии есть
    старое завершённое интервью и поверх него создано новое (ещё `CREATED`), в сводке будет
    `status: "CREATED"` — сводка показывает состояние последней попытки, а не «лучшей».
  - `completedCount` — сколько интервью по вакансии в статусе `COMPLETED`, безотносительно к
    тому, какое из них последнее по времени.
  - `bestScore`/`bestOffer` — `avgScore`/`offerProbability` отчёта с максимальным `avgScore`
    среди ЗАВЕРШЁННЫХ интервью по вакансии (не обязательно последнего по времени); `null` у обоих
    полей, если завершённых интервью по вакансии нет вовсе.
  - `lastActivity` — момент СОЗДАНИЯ самого недавнего интервью по вакансии, а не момент
    последнего ответа внутри него и не `completedAt`.
- **`GET /vacancies/{vacancyId}`** — `200`, `InterviewVacancyDetailResponse`; `404`, если у
  пользователя нет ни одного интервью по вакансии с таким id.
  - `vacancyName`/`employer`/`vacancyUrl`/`experience` — из снапшота самого недавнего по
    `created` интервью по вакансии (как и в сводке из списка).
  - `interviews` — все интервью пользователя по вакансии, СТАРЫЕ первыми (порядок обратный
    списку вакансий); `avgScore`/`offerProbability` — `null`, пока конкретное интервью не
    завершено.
  - `recommendedTrainings` — рекомендации по отстающим навыкам, подробнее ниже.
- **`DELETE /vacancies/{vacancyId}`** — `204`, пустое тело; `404`, если у пользователя нет
  интервью по вакансии.

    {

      "interviewScore": 2.4,

Второй элемент `recommendedTrainings` выше показывает случай без подходящей тренировки: `skill`
и `interviewScore` заполнены всегда, а поля тренировки — `null` разом, это сигнал фронту
предложить создать тренировку по этому навыку.

### Поведение

- **Вакансия группируется по внешнему id, не по внутренним данным.** Каждое создание сессии
  интервью сохраняет собственный неизменный снапшот вакансии (см. «Поведение» сессий выше) — у
  двух интервью по одной вакансии могут быть два разных снапшота. Группировка в `/vacancies` и
  поиск в `/vacancies/{vacancyId}` идут по id вакансии на площадке (`vacancyId`, тот же, что
  зашит в `vacancyUrl`), а не по id снапшота, поэтому несколько интервью по одной вакансии всегда
  попадают в одну группу независимо от того, сколько у них разных снапшотов.
- **Область видимости — только интервью текущего пользователя.** Снапшоты той же вакансии,
  сохранённые при интервью других пользователей, физически лежат в общей таблице снапшотов, но
  в сводку, в детали и в удаление текущего пользователя не попадают.
- **`recommendedTrainings` строится из `weakestSkill` завершённых интервью по вакансии** — того
  же мягкого поля отчёта, что описано в «Поведение» сессий (может быть `null`, тогда интервью в
  рекомендациях не участвует). Навыки схлопываются без учёта регистра. Если один и тот же навык
  оказывается самым слабым в нескольких интервью по вакансии, в рекомендацию попадает не худшая,
  а хронологически ПОСЛЕДНЯЯ оценка этого навыка — данные из более старых интервью с тем же
  навыком перезаписываются более новыми.
- **Сортировка рекомендаций** — по возрастанию `interviewScore`: самый слабый навык (с
  наименьшей оценкой интервью, где он был признан слабым местом) идёт первым.
- **Сопоставление с тренажёром — по названию навыка без учёта регистра.** Навык из отчёта интервью
  ищется среди навыков тренировок пользователя; если совпадение есть, в рекомендацию попадает САМАЯ
  НЕДАВНЯЯ по `created` такая тренировка, независимо от статуса — ещё не начатая (`CREATED`)
  тоже подходит. Более старые тренировки с тем же названием навыка, если их несколько, не
  учитываются вовсе. Совпадения нет — все поля тренировки в рекомендации `null`. Это осознанное
  чтение домена `training` из `interview` (в одну сторону, без записи). `answeredCount`/
  `totalQuestions` считают только основные вопросы тренировки (без уточняющих), как и в самом
  тренажёре; `trainingScore` — `null`, пока тренировка не завершена.
- **Удаление вакансии — это удаление всех интервью пользователя по ней разом.** Единой сущности
  «вакансия» в БД для этого не существует — `DELETE` находит все сессии пользователя с этим id
  вакансии и удаляет их вместе с вопросами, ответами и отчётами (как в удалении одной сессии), а
  заодно — снапшоты вакансии, но только те, на которые ссылались именно эти сессии (снапшоты той
  же вакансии у других пользователей не трогаются). Тренировки из `recommendedTrainings` при этом
  никак не затрагиваются — это независимый домен, связь с ним не более чем сопоставление по
  названию навыка.

## Вспомогательные ручки вакансий — `/api/v1/vacancies`

Отдельный контроллер того же домена `vacancy`, что обслуживает интервью данными о вакансиях hh.ru.
Обе ручки требуют того же access-токена, что и `/api/v1/interview/**` (тот же
`SecurityConfig`, отдельного `permitAll` для `/api/v1/vacancies/**` нет).

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| GET | `/preview` | предпросмотр вакансии по ссылке перед созданием сессии | cookie `access_token` |
| GET | `/status` | живой статус вакансии на hh.ru (активна/в архиве/удалена) | cookie `access_token` |

```java
record VacancyPreviewResponse(String name, String employer, String salary, String experience, String url)

record VacancyStatusResponse(Status status) // enum Status { ACTIVE, ARCHIVED, NOT_FOUND }
```

- **`GET /preview?url=`** — `200` с краткой сводкой по вакансии: название, работодатель, зарплата
  (строкой, может отсутствовать — `null`) и требуемый опыт. Полезно перед `POST
  /api/v1/interview/sessions`, чтобы показать пользователю, по какой вакансии он собирается
  проходить интервью, не тратя вызов LLM. `url` разбирается тем же паттерном hh.ru-ссылки, что и
  `vacancyUrl` в интервью; вакансия не найдена или в архиве — `404`; hh.ru недоступен — `503`.
- **`GET /status?url=`** — `200` с одним из трёх статусов: `ACTIVE`, `ARCHIVED` (снята с
  публикации, но существует) или `NOT_FOUND` (hh.ru вернул 404 — это не ошибка запроса, а
  валидный статус). Результат кешируется на сервере in-memory по id вакансии на **30 минут**
  (`STATUS_TTL`) без вытеснения — повторные проверки одной и той же вакансии в этом окне не
  дёргают hh.ru заново. hh.ru недоступен (не 404, а реальная сетевая/серверная ошибка) — `503`,
  в кеш такой результат не попадает.

Обе ручки не создают и не изменяют сессий интервью и снапшотов вакансий — это чисто читающие
операции для UI (предпросмотр перед стартом и проверка «жива ли ещё вакансия» у уже созданной
сессии).

Пример `VacancyPreviewResponse`:

```json
{
  "name": "Java-разработчик",
  "employer": "ООО Ромашка",
  "salary": "150 000 - 250 000 ₽",
  "experience": "От 1 года до 3 лет",
  "url": "https://hh.ru/vacancy/123456"
}
```

Пример `VacancyStatusResponse`:

```json
{
  "status": "ARCHIVED"
}
```

## Ошибки

Тело ошибки — стандартный `ApiError`:

```json
{
  "timestamp": "2026-07-28T12:00:00",
  "status": "CONFLICT",
  "message": "Conflict.",
  "errors": ["Not all questions answered"]
}
```

| Код | Когда |
|---|---|
| `400` | невалидное тело запроса (пустой `vacancyUrl`/`answerText`, отсутствующий `vote`, `reasons` длиннее 10 элементов или с элементом длиннее 100 символов, `comment` длиннее 2000 символов в `FeedbackRequest`, битый JSON), `vacancyUrl`/`url` не содержит распознаваемую ссылку на вакансию hh.ru, неверный тип path-параметра (`sessionId`/`questionId` не UUID) |
| `401` | нет валидного access-токена (ставит Security-фильтр, тело пустое) |
| `402` | исчерпана квота интервью — остаток по тарифу `0` (`POST /sessions`); подробнее — `docs/billing-api.md` |
| `403` | вопрос, на который отправляется ответ или отзыв, принадлежит другому пользователю |
| `404` | сессия, вопрос или отчёт не найдены (в т.ч. чужие — сессии ищутся сразу с учётом пользователя; отчёт не найден — тот же ответ и у `GET .../report`, и у `POST .../report/feedback`); у пользователя нет интервью по вакансии с указанным `vacancyId` (`GET`/`DELETE /interview/vacancies/{vacancyId}`); вакансия по ссылке не найдена или в архиве (`POST /sessions`, `GET /vacancies/preview`) |
| `409` | у пользователя уже есть незавершённое (`CREATED`/`IN_PROGRESS`) интервью по этой же вакансии (`POST /sessions`, per-vacancy — по другим вакансиям создавать можно); сессия уже завершена (в т.ч. если её завершил параллельный запрос); неотвеченных вопросов не осталось (`.../questions/next`); вопрос уже отвечен; вопрос не принадлежит указанной в пути сессии (в т.ч. при отзыве на вопрос); при `finish` — отвечены не все основные вопросы |
| `503` | hh.ru недоступен (`POST /sessions`, `GET /vacancies/preview`, `GET /vacancies/status`); AI-сервис недоступен или вернул непригодный ответ — при создании сессии (план без первого вопроса, после одного повторного вызова), при `.../questions/next` (вырожденная реплика — пустой текст вопроса вне легитимного случая конца плана, после одного повторного вызова), при `finish` (пустой/слишком короткий итоговый фидбэк, нераспознанная вероятность оффера либо оценено меньше половины кейсов) |

`503` от AI-сервиса и от hh.ru различаются сообщением в `ApiError` (`"AI service unavailable."`
и `"Vacancy service unavailable."` соответственно), но кодом и структурой тела — нет.
