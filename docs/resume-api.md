# Resume API: `/api/v1/resumes`

Резюме пользователя: сервис принимает исходный файл резюме, сохраняет его на сервере, отдаёт
список загруженного и удаляет резюме. Сейчас реализованы загрузка, список и удаление. Принимаются
три формата: PDF, DOCX и TXT. Содержимое файла не читается и не разбирается: сервис определяет формат по первым
байтам и запоминает файл как есть. Загрузка бесплатна, лимиты баланса не списываются.

Ответы и тела ошибок приходят в JSON, а запрос на загрузку отправляется как multipart.

## Аутентификация

Все эндпоинты защищены так же, как остальные закрытые ручки: cookie `access_token`
(см. `docs/auth-api.md`), в браузере запросы идут с `credentials: 'include'`. Резюме всегда
принадлежит пользователю из токена, чужие резюме через API не видны.

## Эндпоинты

| Метод | Путь | Назначение | Авторизация |
|---|---|---|---|
| GET | `/api/v1/resumes` | список своих резюме, новые сверху | cookie `access_token` |
| POST | `/api/v1/resumes` | загрузка файла резюме | cookie `access_token` |
| DELETE | `/api/v1/resumes/{id}` | удаление своего резюме вместе с файлом | cookie `access_token` |

## Запросы

`POST /api/v1/resumes` принимает `multipart/form-data` с одним полем:

| Поле | Тип | Описание |
|---|---|---|
| `file` | файл | исходный файл резюме |

`Content-Type` вручную не ставят: границу (`boundary`) проставляет браузер, когда в `fetch`
передают `FormData`. Фронт так и делает: `formData.append('file', file)`.

Размер ограничен настройками multipart в `application.yml`: файл не больше 5 МБ (`max-file-size`),
весь запрос не больше 6 МБ (`max-request-size`). Превышение любого из двух пределов даёт `413`.
Ещё один параметр, `server.tomcat.max-swallow-size: 10MB`, нужен, чтобы на слишком большую
загрузку Tomcat отвечал `413`, а не обрывал соединение: он дочитывает и отбрасывает остаток тела
до 10 МБ. Если клиент шлёт заметно больше, обрыв всё же возможен, поэтому размер лучше проверять
до отправки (фронт так и делает).

Запрос без части `file` получает `400`. У `GET` нет ни тела, ни параметров.

`DELETE /api/v1/resumes/{id}` принимает только идентификатор резюме в пути (`id` из
`ResumeResponse`), без тела и параметров. Если `id` не похож на UUID, запрос получает `400`.

## Ответы

`GET` и `POST` возвращают резюме в одной форме:

```java
record ResumeResponse(UUID id, String name, Resume.Format format, String originalFilename, int sizeBytes, Instant uploadedAt)
```

| Поле | Описание |
|---|---|
| `id` | идентификатор резюме |
| `name` | название резюме, по которому его различает пользователь, берётся из имени файла |
| `format` | формат исходного файла: `PDF`, `DOCX` или `TXT` |
| `originalFilename` | имя файла, как оно пришло при загрузке (без пути, не длиннее 255 символов) |
| `sizeBytes` | размер файла в байтах |
| `uploadedAt` | момент загрузки, ISO-8601 в UTC |

Значения `format` берутся из enum `Resume.Format`: `PDF`, `DOCX`, `TXT`. Все три доступны при
загрузке, формат выбирает сервис по содержимому файла (см. «Поведение»).

- `GET /api/v1/resumes`: `200` и массив `ResumeResponse`, от новых к старым по моменту загрузки.
  Если резюме нет, массив пустой. Пагинации нет, отдаётся всё.
- `POST /api/v1/resumes`: `201`, заголовок `Location: /api/v1/resumes/{id}` и `ResumeResponse`
  нового резюме в теле. Эндпоинта `GET /api/v1/resumes/{id}`, на который указывает `Location`,
  пока нет (на этом пути есть только `DELETE`), переходить по этому адресу не нужно: все данные
  уже в теле ответа.
- `DELETE /api/v1/resumes/{id}`: `204` без тела. Повторный запрос на тот же `id` получает `404`,
  поэтому «уже удалено» клиент может считать итогом, а не сбоем.

## Поведение

- **Формат определяется по первым байтам.** Заголовок `Content-Type` части `file` не
  учитывается. Проверки идут по порядку, срабатывает первая подходящая:
  1. Если в первых 1024 байтах встречается `%PDF-`, это `PDF`.
  2. Если файл начинается с ZIP-сигнатуры (`PK\x03\x04`), это `DOCX`, но только когда имя файла
     заканчивается на `.docx` (регистр не важен). Любой другой ZIP получает `422` с деталью
     `Unsupported format`. Архив при этом не открывается, поэтому переименованный в `.docx`
     xlsx или другой ZIP-файл сохранится как `DOCX`.
  3. Если файл начинается с сигнатуры OLE2 (старый `.doc`, а также DOCX под паролем) или RTF
     (`{\rtf`), ответ `422` с деталью `Legacy format`.
  4. Остальное пробуется как текст и при успехе получает `TXT`. Файл декодируется как строгий
     UTF-8 (BOM допускается), а если не получилось, как Windows-1251. Кодировка нигде не
     хранится. Файл не считается текстом, если в нём есть байт `NUL` или больше 1% управляющих
     символов (табуляция, перевод строки, возврат каретки и form feed не в счёт). Тогда ответ
     `422` с деталью `Unsupported format`.
  5. Пустой файл получает `422` с деталью `Unsupported format`.

  Расширение имени учитывается только на втором шаге, чтобы отличить DOCX от прочего ZIP. На
  выбор формата в остальных случаях оно не влияет: файл `cv.docx` с PDF внутри сохранится как
  `PDF`, а `cv.pdf` с обычным текстом как `TXT`. Текстовый файл со строкой `%PDF-` в первых
  1024 байтах тоже будет принят как `PDF`.
- **Содержимое не проверяется и не извлекается.** Сигнатура ещё не гарантирует, что файл целый и
  открывается. Сервис не читает текст резюме, не проверяет, что это действительно резюме, а не
  другой документ, и не ищет в нём вредоносное содержимое.
- **Название берётся из имени файла.** Сначала из имени отбрасывается путь (всё до последнего `/`
  или `\`; некоторые клиенты присылают полный путь) и крайние пробелы. Затем от результата
  отрезается одно расширение `.pdf`, `.docx` или `.txt` (регистр не важен), а серия пробелов
  внутри сжимается до одного. Остальные точки остаются в названии, как и любые другие
  расширения: `Иванов Java.pdf` даёт название `Иванов Java`, `v2.1 резюме` остаётся
  `v2.1 резюме`, а `cv.final` остаётся `cv.final`. Название обрезается до 100 символов. Если
  после этих шагов оно пустое (имя не пришло вовсе или состоит из одного расширения, например
  `.pdf`), название равно `Резюме`. Название не уникально: два файла с одним именем дают два
  резюме с одним названием.
- **Имя файла.** В `originalFilename` лежит то же имя без пути и крайних пробелов, обрезанное до
  255 символов. Если имя пустое или не пришло вовсе, подставляется `resume.<расширение>` по
  определённому формату: `resume.pdf`, `resume.docx` или `resume.txt`. Изменить название или
  имя после загрузки пока нельзя: эндпоинтов изменения нет.
- **Файл хранится на диске сервера.** В базе лежат только метаданные из `ResumeResponse`, сам
  файл записывается в каталог `RESUME_STORAGE_DIR` (по умолчанию `data/resumes`) по пути
  `{идентификатор пользователя}/{идентификатор резюме}`, без расширения. Запись идёт через
  временный файл с атомарным переименованием, поэтому недописанный файл под итоговым именем не
  появляется. Если после записи файла не удалось сохранить строку в базе, а также если запись
  отклонена повторной проверкой лимита (см. ниже), файл удаляется. Скачивания файла через API
  пока нет.
- **У пользователя не больше 3 резюме.** Лимит проверяется дважды. Первая проверка идёт в самом
  начале, до определения формата: если резюме уже три, сервис сразу отвечает `409` с деталью
  `Resume limit reached` и файл не разбирает. Вторая проверка идёт при записи строки в базе, в
  транзакции под блокировкой `pg_advisory_xact_lock` на пользователя. Она нужна для параллельных
  загрузок: когда у пользователя два резюме и приходят две загрузки сразу, обе проходят первую
  проверку, но вторая в транзакции видит уже три резюме, получает `409`, и записанный ею файл
  удаляется. Четвёртого резюме не появится. Повторная загрузка того же файла создаёт новое резюме,
  пока лимит не достигнут. Освободить место можно удалением резюме (см. ниже).
- **Не больше 10 загрузок в сутки.** Это отдельный лимит от числа резюме. Он считается на
  пользователя в бакете `resume-upload`: по умолчанию 10 загрузок за 24 часа, настраивается
  переменными `RESUME_UPLOAD_RATE_LIMIT_LIMIT` и `RESUME_UPLOAD_RATE_LIMIT_WINDOW`. Превышение
  даёт `429` с деталью `Too many requests`. Окно фиксированное: оно открывается на первой
  засчитанной загрузке и закрывается по истечении срока, а не в полночь. Счётчик хранится в
  памяти сервера и сбрасывается при рестарте. Засчитываются только загрузки, прошедшие
  проверку числа резюме и проверку формата, так что отказы `409` и `422` суточный лимит не
  тратят. Слот тратится и в том случае, если после этого запись не удалась: из-за повторной
  проверки лимита (`409`) или сбоя записи (`500`). Удаление резюме потраченный слот не
  возвращает: загрузить и удалить десять раз за сутки значит исчерпать суточный лимит.
- **Удаление окончательное.** Резюме и его файл не восстановить, корзины и отмены нет. Ручка
  удаляет только своё резюме: чужое и несуществующее неотличимы и дают одинаковый `404` с деталью
  `Resume not found`, а не `403`, чтобы по ответу нельзя было узнать, существует ли чужой `id`.
  Строка в базе удаляется в транзакции, а исходный файл с диска стирается уже после её
  коммита и асинхронно, поэтому `204` не гарантирует, что файл исчез в ту же секунду. Если
  транзакция откатилась, файл остаётся на месте. Если удалить файл не удалось, ответ всё равно
  `204`: ошибка только пишется в лог сервера (уровень ERROR, с идентификаторами пользователя и
  резюме), а файл остаётся на диске без строки в базе. Сверки и повторной очистки нет. Для
  пользователя это не заметно: резюме из списка пропадает, и место в лимите в 3 резюме
  освобождается сразу после ответа.
- **Порядок проверок.** Размер файла (`413`), затем «уже 3 резюме» (`409`), затем формат
  (`422`), затем суточный лимит (`429`), затем запись с повторной проверкой «уже 3» (`409`).
  Токен проверяется раньше всех, поэтому `401` идёт первым. Если запрос нарушает сразу несколько
  правил, придёт ошибка той проверки, что стоит в списке раньше.
- **Двойной клик даёт один результат.** Если тот же пользователь отправляет тот же файл
  (совпадает SHA-256 содержимого), пока первая загрузка ещё идёт, вторая не создаёт новое резюме,
  а ждёт первую и получает тот же ответ, включая ошибку. Имя файла в сравнении не участвует:
  один и тот же файл под двумя именами в этот момент тоже считается одной загрузкой. Защита
  работает в памяти одного экземпляра сервера. Суточный лимит такая ожидающая загрузка не тратит.
- **Лимиты баланса не списываются.** Загрузка не платная операция, баланс не проверяется и не
  меняется, `402` у этих эндпоинтов не бывает.

## Клиент на фронте

Клиент лежит в `frontend/src/features/resume/`, страница списка в `frontend/src/pages/resume/`.

- `resumeApi.list()`, `resumeApi.upload(file)` и `resumeApi.remove(id)` зовут `GET`, `POST` и
  `DELETE` через общий `apiFetch`, с теми же cookie и обновлением токена по `401`, что и
  остальные ручки.
- Поле выбора файла в интерфейсе ограничено `accept=".pdf,.docx,.txt"`. Это подсказка
  браузеру, не защита: решает бэк.
- До отправки страница проверяет выбранный файл (`files.ts`). Сначала расширение (регистр не
  важен): если оно не `.pdf`, `.docx` и не `.txt`, пользователь видит «Поддерживаются только PDF,
  DOCX и TXT.», и запрос не уходит. Из-за этого файл с расширением `.doc` или `.rtf` до бэка не
  доходит, а `Legacy format` приходит, когда старый документ Word переименован в разрешённое
  расширение или DOCX защищён паролем. Затем размер: файл больше 5 МБ (5 * 1024 * 1024 байт)
  отсекается с текстом «Файл больше 5 МБ.», тоже без запроса. Проверка быстрая, окончательное
  решение за бэком.
- Число резюме страница знает из списка. Когда их три (`MAX_RESUMES`), кнопка загрузки в шапке
  неактивна, а над списком появляется подсказка «У тебя 3 резюме. Удали одно, чтобы загрузить
  новое.». Пока резюме нет вовсе, кнопка есть только в пустом состоянии и всегда активна. Если
  лимит всё же сработал на бэке (список устарел или загрузку запустили в другой вкладке),
  приходит `409` и показывается текст из таблицы ниже. Кнопка неактивна и пока загрузка идёт, так
  что двойной клик на странице обычно не срабатывает, а серверная защита от него страхует другие
  клиенты и параллельные вкладки.
- После успешной загрузки хук `useUploadResume` отправляет цель Метрики `resume_upload` и
  инвалидирует кэш списка (`['resumes']`), так что список перечитывается заново.
- Удаление запускает кнопка «Удалить» на карточке резюме. Сначала открывается диалог
  подтверждения «Удалить резюме?» с текстом о том, что резюме будет удалено вместе с файлом, и
  только после согласия уходит запрос (хук `useDeleteResume`). Пока запрос идёт, кнопка
  неактивна. Список перечитывается и после успеха, и после ошибки, так что устаревшая карточка
  не остаётся. Ошибка показывается под кнопкой.
- Детали из `ApiError.errors[0]` переводятся в `errors.ts` (`resumeErrorMessage`): сопоставление
  идёт по точному тексту детали, переводы собраны в таблице ошибок ниже. Всё, чего в
  `errors.ts` нет, идёт через общий `getErrorMessage`, то есть показывается поле `message` тела
  ошибки как есть.

## Ошибки

Тело ошибки такое же, как у всех остальных ручек:

```json
{
  "timestamp": "2026-10-01T12:00:00",
  "status": "UNPROCESSABLE_CONTENT",
  "message": "Unprocessable content.",
  "errors": ["Unsupported format"]
}
```

Отказы `POST /api/v1/resumes` в порядке проверок (кроме `401`, он идёт первым):

| Код | Деталь (`errors[0]`) | Когда | Текст на фронте |
|---|---|---|---|
| `401` | нет (все эндпоинты) | нет токена или токен недействителен | отдельного текста нет, действует общий сценарий `apiFetch` с обновлением токена |
| `413` | `File too large` | файл больше 5 МБ или весь запрос больше 6 МБ | «Файл больше 5 МБ.» |
| `400` | стандартное сообщение Spring о том, что нет части `file` | в `multipart` нет части `file` | перевода нет, показывается `message` тела: `Validation Failed` |
| `409` | `Resume limit reached` | у пользователя уже 3 резюме: проверка до определения формата или повторная при записи | «У тебя уже 3 резюме. Удали одно, чтобы загрузить новое.» |
| `422` | `Unsupported format` | пустой файл, ZIP без расширения `.docx`, бинарный файл, не похожий на текст | «Поддерживаются только PDF, DOCX и TXT.» |
| `422` | `Legacy format` | старый или защищённый паролем документ Word либо RTF | «Старые файлы Word, RTF и документы Word под паролем не поддерживаются. Сохрани файл как DOCX без пароля или PDF.» |
| `429` | `Too many requests` | больше 10 загрузок в сутки на пользователя, считаются только прошедшие проверки числа резюме и формата | «Слишком много загрузок за сутки. Попробуй завтра.» |
| `500` | `Unexpected error occurred` | сбой записи файла на диск или сохранения в базу | перевода нет, показывается `message` тела: `Internal server error` |

Поле `message` тела у каждого кода своё: `Content too large.` у `413`, `Conflict.` у `409`,
`Unprocessable content.` у `422`, `Too many requests.` у `429`, `Validation Failed` у `400`,
`Internal server error` у `500`. Для обработки на клиенте опирайся на код и деталь, как это
делает `errors.ts`.

`400` из интерфейса получить нельзя: страница всегда кладёт файл в `FormData`. Код нужен тем, кто
вызывает API напрямую. У `GET /api/v1/resumes` возможны только `200` и `401`.

Отказы `DELETE /api/v1/resumes/{id}`:

| Код | Деталь (`errors[0]`) | Когда | Текст на фронте |
|---|---|---|---|
| `401` | нет | нет токена или токен недействителен | отдельного текста нет, действует общий сценарий `apiFetch` с обновлением токена |
| `400` | `Parameter 'id' should be of type java.util.UUID` | `id` в пути не UUID | перевода нет, показывается `message` тела: `Validation Failed` |
| `404` | `Resume not found` | резюме нет, оно уже удалено или принадлежит другому пользователю | «Резюме уже удалено.» |

У этой ручки `message` при `404` равно `The required object was not found.`. Другие коды
невозможны: баланс не проверяется, лимитов на удаление нет, а сбой удаления файла до клиента не
доходит и остаётся в логе. `400` из интерфейса получить нельзя: `id` берётся из списка.
