# Speech API — `/api/v1/speech/stt`

Потоковое распознавание речи: браузер шлёт звук с микрофона, сервер отвечает распознанным
текстом, пока пользователь ещё говорит. Ручка одна и работает по **WebSocket** — обычного
REST здесь нет, в Swagger она не отображается.

Ручка ничего не знает о том, куда пойдёт текст: её одинаково используют прогон интервью
по вакансии и прогон тренажёра навыков. Ни сессия, ни вопрос в неё не передаются, ответ
пользователь отправляет отдельным REST-запросом своего домена.

Аудио нигде не сохраняется: оно проходит через память сервера в сервис распознавания
и не пишется ни на диск, ни в базу.

## Адрес и аутентификация

```
ws://localhost:8080/api/v1/speech/stt     (dev)
wss://<хост>/api/v1/speech/stt            (прод)
```

Рукопожатие — обычный HTTP-запрос, поэтому работает та же аутентификация, что у REST:
cookie `access_token` уходит автоматически, отдельного заголовка или токена в query-параметре
не нужно. Токен в адресе передавать нельзя — он попадёт в логи и историю браузера.

Без действующего access-токена рукопожатие завершается статусом `401`, соединение не
открывается: браузер сообщит об этом событием `error`, а затем `close` с кодом `1006`.
Если access-токен истёк, сначала обновите его через `POST /api/v1/auth/refresh`,
потом открывайте сокет.

Проверяется и источник запроса: `Origin` должен быть в списке разрешённых
(`app.security.cors.allowed-origins`, тот же, что у REST). Чужой источник — рукопожатие
отклоняется со статусом `403`.

## Протокол

| Направление | Тип фрейма | Содержимое |
|---|---|---|
| клиент → сервер | бинарный | очередной кусок аудио |
| клиент → сервер | текстовый | `stop` — речь закончена |
| сервер → клиент | текстовый | событие распознавания, JSON |

Любой текст, кроме `stop`, сервер игнорирует.

## Формат аудио

Сырой LPCM без заголовков:

| Параметр | Значение |
|---|---|
| Кодирование | signed 16-bit little-endian (LINEAR16_PCM) |
| Частота дискретизации | 16 000 Гц |
| Каналов | 1 (моно) |
| Язык | ru-RU |

Контейнеры не поддерживаются: WebM/Opus от `MediaRecorder` сервер не примет. В браузере звук
удобно готовить через `AudioWorklet` — `AudioContext({ sampleRate: 16000 })` сам сделает
пересчёт частоты, останется перевести `Float32` в `Int16`.

Рекомендуемый размер куска — 400 мс, то есть 6400 сэмплов или 12 800 байт. Предел одного
бинарного фрейма — 64 КБ; более крупный фрейм разорвёт соединение.

## События

Сервер шлёт текстовые сообщения одного вида:

```java
record SttEvent(Type type, String text)   // Type: PARTIAL | FINAL | REFINEMENT | ERROR
```

```json
{ "type": "REFINEMENT", "text": "Spring поднимает контекст один раз при старте." }
```

| `type` | Что это | Что с этим делать |
|---|---|---|
| `PARTIAL` | промежуточная гипотеза, текст ещё меняется | показывать бегущей подсказкой под полем ввода |
| `FINAL` | фраза закончена, текст без нормализации — без пунктуации, числа словами | придержать; пригодится, только если нормализация не придёт |
| `REFINEMENT` | та же фраза после нормализации: пунктуация, числа цифрами | дописать в поле ответа — это итоговый текст |
| `ERROR` | распознавание оборвалось, в `text` — описание | показать пользователю; следом сервер закроет соединение |

`FINAL` и `REFINEMENT` — не два разных куска речи, а один и тот же кусок дважды. Складывать
их нельзя: в поле ответа идёт `REFINEMENT`, а `FINAL` нужен как запасной вариант на случай,
когда соединение закрылось, не дождавшись нормализации.

Событий может не быть вовсе — если пользователь молчал, сервер просто закроет соединение
после `stop`.

## Жизненный цикл сессии

1. Клиент открывает сокет.
2. Шлёт бинарные фреймы с аудио и получает `PARTIAL`, а по мере окончания фраз — `FINAL`
   и `REFINEMENT`.
3. Закончив говорить, шлёт текстовое `stop`.
4. Сервер дожидается последних гипотез, отдаёт их и **сам закрывает соединение** кодом `1000`.

Пункты 3 и 4 важны именно в таком порядке: **клиенту закрывать сокет самому не нужно**.
Нормализованный финал приходит уже после того, как аудио кончилось, — закрыв соединение
вместо отправки `stop`, клиент потеряет ровно тот текст, ради которого всё затевалось.

Одна сессия — один ответ. Для следующего ответа сокет открывается заново.

## Лимиты и ошибки

- **Частота рукопожатий** — по IP, по умолчанию 60 в час (`STT_RATE_LIMIT_LIMIT` /
  `STT_RATE_LIMIT_WINDOW`). При превышении рукопожатие отклоняется со статусом `429`,
  сокет не открывается.
- **Длительность записи** — не больше четырёх минут аудио на сессию (около 7,3 МБ).
  Дойдя до предела, сервер прекращает приём: последние гипотезы он ещё отдаст, а дальнейшие
  фреймы отбросит молча и закроет соединение кодом `1000`. Клиенту стоит держать
  собственный таймер, но полагаться на него нельзя — предел стоит на сервере.
- **Сбой распознавания** — сервер шлёт `{"type":"ERROR"}` и закрывает соединение
  кодом `1011` с причиной `Recognition failed`. Всё, что было распознано до сбоя,
  остаётся у клиента.

Коды закрытия, которые клиент считает нормальными: `1000` (штатное завершение) и `1005`
(закрытие без кода). Любой другой — повод показать пользователю, что связь прервалась;
наговоренный текст при этом терять не нужно.

## Ошибки в браузере

Ошибки микрофона к API отношения не имеют, но разбирать их полезно в том же месте:

| Ситуация | Как выглядит |
|---|---|
| нет `getUserMedia` или `AudioWorkletNode` | браузер не поддерживает запись |
| `NotAllowedError` | пользователь запретил доступ к микрофону |
| `NotFoundError` | микрофон не подключён |
| `NotReadableError` | микрофон занят другим приложением |

Доступ к микрофону нужно запрашивать **до** открытия сокета: иначе вызов уходит за пределы
пользовательского жеста и Safari его отклоняет.
