# Training API - `/api/v1/training`

Тренажёр для отработки конкретного навыка перед собеседованием. Пользователь указывает навык,
который хочет прокачать, профессию как контекст (в каком амплуа этот навык нужен) и уровень
сложности вопросов - и проходит серию самостоятельных вопросов, в конце получая отчёт с
поразборным фидбэком по каждому вопросу и средним баллом.

Все вопросы сессии подбираются целиком уже при создании: сначала сэмплируются из курируемого
банка вопросов (`content.question_bank`, наполняется офлайн, отдельно от рантайма), а недостающие
до лимита добираются одним батч-вызовом LLM. Когда пачка вопросов кончилась, у пользователя есть
альтернатива разбору - взять ещё одну пачку в ту же сессию (`.../questions/more`, вопросы новые,
всего в тренировке не больше 50). Уже пройденную тренировку можно пройти заново с теми же
вопросами (`.../restart`). Дальше, пока идёт сама тренировка
(`.../questions/next`, отправка ответа), LLM не вызывается вовсе - вопрос просто отдаётся по
порядку, ответ просто сохраняется. LLM снова подключается только по требованию (посмотреть
эталонный ответ на конкретный вопрос) и один раз в конце - оценить все ответы и написать итоговый
отчёт. Уточняющих вопросов, в отличие от интервью по вакансии, в тренажёре нет: каждый вопрос
самостоятелен - свой ответ, своя оценка, свой фидбэк. Все тела запросов и ответов - JSON.

> **Интервью по вакансии - отдельный домен.** Этот документ описывает только тренажёр
> (`/api/v1/training`). Интервью по вакансии - контракт `/api/v1/interview`, он описан в
> `docs/interview-api.md`.

## Доступ

Домен закрыт целиком: `SecurityConfig` требует аутентификации на любой путь, не входящий
в `/api/v1/auth/**` и Swagger. Ко всем ручкам `/api/v1/training/**` нужен валидный
access-токен - cookie `access_token` (для Swagger в dev поддержан fallback
`Authorization: Bearer <accessToken>`). Без него - `401` с пустым телом (это делает
Security-фильтр, а не контроллер, поэтому тело `ApiError` не приходит).

Сессии и вопросы привязаны к пользователю из токена. Большинство ручек (получение
сессии, список, следующий вопрос, добор вопросов, завершение, перезапуск, отчёт, отзыв на отчёт,
удаление) сами ищут ресурс с учётом
`userId`, поэтому чужой ресурс для них просто "не существует" - ответ `404`. Исключение -
отправка ответа (`POST .../questions/{questionId}`), просмотр эталонного ответа
(`GET .../questions/{questionId}/reference-answer`) и отзыв на вопрос
(`POST .../questions/{questionId}/feedback`): во всех трёх ручках вопрос сначала ищется по
`questionId` без учёта владельца, и если он оказывается чужим, это разбирается явно - ответ
`403`. Там же отдельно проверяется, что найденный вопрос действительно принадлежит сессии из
пути `sessionId`, а не какой-то другой сессии того же пользователя - если нет, `409` (вопрос
существует и доступен, просто запрос обратился не к той сессии).

## Справочные значения

`TrainingSession.Level` сериализуется не по имени константы, а по русскому лейблу - это
уровень сложности вопросов, а не грейд должности: тренажёр рассчитан и на профессии вне IT,
где `Junior`/`Middle`/`Senior` не в ходу. Английский код остаётся внутренним: под ним лежат
уровни в банке вопросов (`content.question_bank.levels`) и по нему выбирается один из четырёх
LLM-агентов, генерирующих вопросы (`training-question-generator-{noexp|junior|middle|senior}`);
наружу код не отдаётся. От уровня зависит только генератор вопросов - оценка ответа от уровня
не зависит вообще: агент-оценщик один на все уровни (`training-reviewer`) и меряет полноту
ответа относительно конкретно заданного вопроса, а не относительно ожиданий от грейда.

`TrainingSession.Status` кастомного лейбла не имеет, сериализуется по имени константы.

- **TrainingSession.Level** - `Базовый`, `Начинающий`, `Уверенный`, `Продвинутый` (по
  возрастанию сложности; внутренние коды - `noexp`, `junior`, `middle`, `senior`
  соответственно, в контракте не встречаются).
- **TrainingSession.Status** - `CREATED`, `IN_PROGRESS`, `COMPLETED`.

### Навык и профессия

Тренируется навык (`skill`), а профессия (`profession`) - уточняющий контекст, под каким углом
про этот навык спрашивать (например, `SQL` для `Java-разработчика` и `SQL` для
`Аналитика данных` - разный набор вопросов). Оба поля обязательны, свободный текст
(не enum) до 100 символов каждое.

Перед созданием сессии оба поля проходят проверку распознавания. Она проходит без обращения к
LLM, если оба названия уже известны словарю: профессия найдена, и навык найден в словаре
**именно этой профессии** - словарь навыков скоуплен по профессии (одна и та же строка навыка
под разными профессиями - разные записи с независимым статусом одобрения). Статус записи при
этом не важен: в словарь попадает только распознанный ввод, поэтому известное название повторно
у LLM не переспрашивается - иначе один и тот же ввод в разные дни получал бы разные варианты
названия и плодил синонимы. Если хоть одно из полей словарю неизвестно, бэк вызывает LLM-агента
`input-normalizer` с обоими полями сразу, одним вызовом. Дальше проверяется вердикт
распознавания по каждому неизвестному словарю полю отдельно, **сначала навык, потом
профессия**: не распознан навык - `422` с деталями `Skill not recognized`, до проверки
профессии дело не доходит; распознан навык, но не распознана профессия - `422` с
`Profession not recognized`.

Известное словарю поле подставляется в сессию в том написании, в каком лежит в словаре: ввод
"разработчик на JAVA" даёт сессию с профессией "Java-разработчик". Признанный, но не словарный
ввод канонизируется независимо по каждому полю по списку подсказок LLM
(`skillSuggestions`/`professionSuggestions` - тех же полей, что отдаёт `/normalize`; пригоден
непустой вариант не длиннее 100 символов): берётся первая подсказка, которая уже есть в
словаре, и в сессию идёт её словарное написание; если словарю не известна ни одна - первая
пригодная подсказка как есть. Поэтому `skill`/`profession` в ответе `POST /sessions` могут
отличаться от того, что было отправлено в запросе: "ДЖАВИСТ" на входе даёт сессию с профессией
"Java-разработчик" на выходе - это не ошибка, а нормализация. Если LLM распознала поле, но не
предложила ни одной пригодной подсказки (пустой список, только пробельные строки или все
варианты длиннее 100 символов) - сохраняется исходный текст пользователя, без ошибки.

Названия навыка и профессии - и присланные пользователем, и пришедшие от LLM - перед сравнением
и записью приводятся к сравнимому виду: типографские дефисы и тире (в том числе неразрывный)
заменяются на обычный `-`, неразрывные и узкие пробелы - на обычный, повторы пробелов
схлопываются, края обрезаются. Регистр при этом сохраняется: сравнение имён и без того идёт
без учёта регистра. Без этой чистки "Java-разработчик" с неразрывным дефисом заводил бы в
словаре двойника уже одобренной записи, а вопросы банка по такому навыку не находились бы.

Совпадение со словарём ищется не по самой строке, а по ключу сравнения: название приводится к
нижнему регистру, пунктуация отбрасывается (кроме `+` и `#` внутри слова, иначе `C`, `C++` и
`C#` стали бы одним навыком), выбрасываются служебные слова (`на`, `по`, `для`, `и`, `of`,
`for`, `the` и подобные), а оставшиеся слова сортируются по алфавиту без повторов. У
"Java-разработчик" и "Разработчик на Java" ключ одинаковый - это одна запись словаря, а не две.
Ключ определяет и уникальность в словаре: у профессий она по ключу, у навыков - по паре
(профессия, ключ). На разный набор слов ключ не действует: "Spring JPA" и "Spring Boot JPA"
остаются разными записями - такие пары сводит уже LLM (см. ниже).

Чтобы LLM не предлагала синоним уже принятого названия, вместе с вводом ей передаются
кандидаты из словаря: до 10 названий навыков и до 10 названий профессий, у которых есть общее
значащее слово с вводом (по всему словарю, вне зависимости от статуса, самые используемые
первыми). Агент обязан поставить подходящий по смыслу вариант из этого списка первым в своих
подсказках дословно. Так "Spring Boot Jpa" при уже существующем "Spring JPA" превращается в
существующую запись, а не в двойника.

Любое успешное создание сессии (независимо от того, потребовался LLM или нет) пополняет оба
словаря: счётчик `usage_count` у профессии и у навыка увеличивается на единицу, а если такой
записи ещё не было - она создаётся со статусом `AUTO`. `AUTO`-записи копятся невидимо: наружу
(`/options`, `/suggest/*`) отдаются только записи со статусом `APPROVED`, до ручного
кураторства они подсказкой не становятся. Если проверка распознавания отклонила ввод (`422`),
сессия не создаётся и словарь не пополняется.

`GET /options` отдаёт `skills` и `professions` отдельными списками - топ-20 каждого по
убыванию `usage_count`, просто подсказки для быстрого выбора в UI, ввод любого другого
значения так же валиден. У навыков агрегация особая: поскольку навык в словаре - это пара
(профессия, название), а не просто название, одноимённые навыки разных профессий в этом
списке схлопываются в один пункт (сравнение без учёта регистра), а их `usage_count`
суммируется.

### Подсказки (`/suggest/professions`, `/suggest/skills`)

`GET /suggest/professions?query=...` и `GET /suggest/skills?query=...&profession=...` - живые
подсказки для комбобокса на фронте (debounce ввода - забота клиента, бэк его не делает). Обе
ручки отдают до 7 названий (`SUGGEST_LIMIT`) из словаря, отобранных по подстроке `query`
(регистронезависимо) и отсортированных: сначала совпадения по началу названия, затем по
убыванию `usage_count`, затем по алфавиту. Как и в `/options`, показываются только одобренные
записи словаря (`APPROVED`) - автозаписи из чужого свободного ввода в подсказки не попадают.
Подсказка - необязательный ускоритель ввода: `CreateSessionRequest.skill`/`profession`
по-прежнему принимает любую строку, в том числе не встречавшуюся в словаре.

- `profession` у `/suggest/skills` необязателен. Навык вводится первым полем мастера, ещё до
  выбора профессии, поэтому без `profession` подсказки собираются по всему словарю: одноимённые
  навыки разных профессий схлопываются в одну строку (без учёта регистра), их `usage_count`
  суммируется. С переданной непустой `profession` подсказки ограничиваются навыками именно этой
  профессии (значение резолвится в словаре по ключу сравнения, поэтому годится любое написание
  названия: "разработчик на java" находит навыки записи "Java-разработчик"; нет такой профессии
  в словаре - пустой список, а не `404`: профессия по-прежнему может быть введена вручную).
- `query` короче 2 символов после `strip()` - у обеих ручек `200` с пустым массивом (это не
  ошибка, комбобоксу просто нечего показать на один введённый символ). Отсутствие самого
  параметра `query` - `400` у обеих ручек; отсутствие `profession` у `/suggest/skills` ошибкой
  не является, он необязателен.
- Спецсимволы LIKE (`%`, `_`) в `query` экранируются перед поиском - ищутся буквально, как
  обычные символы, а не как wildcard-маска.
- Лимит частоты - 60 запросов в минуту с одного IP (`app.security.rate-limit.suggest.limit/window`,
  по умолчанию `SUGGEST_RATE_LIMIT_LIMIT=60`, `SUGGEST_RATE_LIMIT_WINDOW=1m`). Настройка одна на обе
  ручки, но счётчики **раздельные**: `/suggest/professions` и `/suggest/skills` тратят каждый свои
  60 запросов, набор одного поля мастера не съедает лимит второго. При превышении - `429`.

### Распознавание ввода (`POST /normalize`)

Подсказки словаря (`/suggest/*`) покрывают только известные варианты. Если пользователь
печатает навык или профессию вручную мимо подсказок (например, "джава дев"), `/normalize` даёт
шаг подтверждения перед созданием сессии: отправляет оба введённых текста LLM-агенту
`input-normalizer` (Yandex AI Studio) вместе с похожими названиями из словаря и возвращает,
распознаваемы ли навык и профессия, подходит ли навык профессии и какими каноническими
названиями их стоит заменить. Названия, уже принятые в словаре, агент ставит первыми - поэтому
подсказки чаще всего ведут в существующую запись, а не в её синоним.

Сам вердикт распознавания - не только подсказка: `POST /sessions` повторяет ту же проверку на
бэке (известное словарю - без LLM, иначе тот же агент `input-normalizer`) и отклоняет
нераспознанный ввод `422`-м (см. "Навык и профессия" выше), поэтому UI стоит блокировать
отправку при `skillRecognized=false` или `professionRecognized=false`. Выбор предложенного
варианта из `skillSuggestions`/`professionSuggestions` для пользователя необязателен, но
результат не гарантирует сохранение его формулировки: если поле словарю неизвестно,
`POST /sessions` сам подставит вместо введённого текста подсказку - поэтому уже здесь, по
ответу `/normalize`, можно увидеть, каким текстом в итоге станут `skill`/`profession` после
создания сессии. Сама ручка `/normalize` ничего не создаёт и не сохраняет.

Оба поля запроса обязательны (`@NotBlank`) и анализируются всегда: все пять полей
`NormalizeInputResponse` заполнены в каждом ответе.

- `skillFitsProfession` - мягкий сигнал о том, что навык логически не подходит указанной
  профессии (например, `React` при профессии "Повар"). Это не ограничение контракта: UI может
  показать предупреждение, но бэк не запрещает создать сессию с таким сочетанием.
- Вызов платный (обращение к LLM), поэтому ограничен собственным, более строгим лимитом
  частоты - 10 запросов в минуту с одного IP (`app.security.rate-limit.normalize.limit/window`,
  по умолчанию `NORMALIZE_RATE_LIMIT_LIMIT=10`, `NORMALIZE_RATE_LIMIT_WINDOW=1m`), независимым
  от лимита `/suggest/*`. При превышении - `429`.
- При недоступности AI-сервиса - `503`, как и у прочих LLM-ручек домена (`POST /sessions`,
  `POST .../questions/more`, `GET .../reference-answer`, `POST .../finish`).

## Запросы (DTO)

```java
record CreateSessionRequest(
    @NotBlank @Size(max = 100) String skill,
    @NotBlank @Size(max = 100) String profession,
    @NotNull TrainingSession.Level level)

record SubmitAnswerBody(@NotBlank String answerText)

record NormalizeInputRequest(
    @NotBlank @Size(max = 100) String skill,
    @NotBlank @Size(max = 100) String profession)

record FeedbackRequest(
    @NotNull TrainingUserFeedback.Vote vote,
    @NotNull @Size(max = 10) List<@Size(max = 100) String> reasons,
    @Size(max = 2000) String comment)
```

Все поля `CreateSessionRequest` обязательны: `skill` и `profession` - непустые строки не
длиннее 100 символов, `level` - один из четырёх уровней сложности. У `NormalizeInputRequest`
оба поля обязательны по тем же правилам. `GET /options`, `POST .../questions/next`,
`POST .../questions/more`, `GET .../reference-answer`, `POST .../finish`, `POST .../restart`,
`GET .../report` и `DELETE` тела не принимают.

`FeedbackRequest` - тело обеих ручек отзыва (на вопрос и на отчёт), одинаковое для обеих.
`vote` - `UP` (лайк) или `DOWN` (дизлайк), обязателен. `reasons` - список причин дизлайка, до 10
строк не длиннее 100 символов каждая; поле обязательно как таковое (пустой массив `[]`, а не
отсутствующее поле) - у лайка ожидается пустым по соглашению фронта, но бэк это не
перепроверяет и непустой `reasons` при `vote: "UP"` не отклонит. `comment` - необязательный
свободный текст до 2000 символов.

## Ответы

```java

    List<String> skills, List<String> professions, List<TrainingSession.Level> levels,
    int questionCap, int maxQuestions, int minAnswersToFinish)

    UUID id, String skill, String profession, TrainingSession.Level level,
    TrainingSession.Status status, int answeredCount, int totalQuestions,

    UUID questionId, int orderIndex, String questionText,
    String answerText, Integer score, String feedback)

    UUID reportId, UUID sessionId, String skill, String profession,
    TrainingSession.Level level, Double avgScore, String overallFeedback, Instant generatedAt,
```

- **`GET /options`** - `200`, `TrainingOptionsResponse`. `skills`/`professions` - топ-20
  каждого по убыванию частоты использования, только подсказки для UI (см. "Навык и профессия"
  выше). `questionCap` = 10 (размер пачки: столько вопросов создаётся при старте и столько
  добавляет `.../questions/more`), `maxQuestions` = 50 (потолок вопросов в одной тренировке,
  дальше добор недоступен), `minAnswersToFinish` = 3 (минимум отвеченных вопросов, чтобы
  завершение стало доступно).
- **`GET /suggest/professions`**, **`GET /suggest/skills`** - `200`, тело - просто JSON-массив
  строк (не обёрнут в объект), до 7 элементов; пустой массив - валидный ответ для короткого
  запроса или неизвестной профессии, а не ошибка (см. "Подсказки" выше).
- **`POST /normalize`** - `200`, `NormalizeInputResponse`. Все пять полей заполнены всегда:
  оба поля запроса обязательны, поэтому анализируются оба.
- **`POST /sessions`** - `201` с `TrainingSessionResponse` и заголовком `Location`
  (`/sessions/{id}`). Свежесозданная сессия: `status = CREATED`, `answeredCount = 0`.
  `skill`/`profession` в ответе - уже канонизированные значения (см. "Навык и профессия"
  выше), они могут отличаться от того, что было отправлено в `CreateSessionRequest`.
  Нераспознанный навык или профессия - `422`, сессия не создаётся, словарь не пополняется.
  Сам ответ не содержит списка вопросов - они уже подобраны на бэке (см. "Поведение" ниже), но
  отдаются пользователю по одному через `.../questions/next`.
- **`GET /sessions`** - `200`, `PagedModel<TrainingSessionResponse>` (страница Spring
  Data: поле `content` с массивом сессий плюс метаданные страницы). Поддерживаются
  стандартные query-параметры Spring Pageable - `page`, `size`, `sort`; по умолчанию
  сортировка `created,desc` (новые сессии первыми).
- **`GET /sessions/{sessionId}`** - `200`, `TrainingSessionResponse` с актуальным
  `answeredCount`.
- **`POST .../questions/next`** - `200`, `TrainingQuestionResponse`: первый неотвеченный
  вопрос сессии по порядку (`orderIndex`, сквозная нумерация 1..N по всей сессии). LLM здесь
  не вызывается вовсе - все вопросы уже существуют с момента создания сессии, ручка просто
  отдаёт следующий. `answerText`, `score`, `feedback` для только что полученного вопроса
  всегда `null`.
- **`POST .../questions/more`** - `200`, `TrainingSessionResponse` с увеличенным
  `totalQuestions`: в сессию добавлена следующая пачка вопросов, забирать их по-прежнему через
  `.../questions/next`. Ручка требует, чтобы все имеющиеся вопросы были отвечены (иначе `409`),
  и упирается в потолок `maxQuestions` (`409`). Новых вопросов по этому навыку и уровню не
  нашлось - `409` с деталью `No new questions available` (см. "Поведение").
- **`GET .../questions/{questionId}/reference-answer`** - `200`, `ReferenceAnswerResponse`. Не
  требует, чтобы вопрос уже был отвечен, и не проверяет статус сессии - эталон можно
  посмотреть до своего ответа и после завершения тренировки, пока сам вопрос существует в БД
  (см. "Поведение").
- **`POST .../questions/{questionId}`** - `204`, пустое тело. Фидбэка в ответе нет - оценка
  появится только в отчёте после `finish`.
- **`POST .../questions/{questionId}/feedback`**, **`POST .../report/feedback`** - `204`,
  пустое тело у обеих. Отзыв нигде обратно не отдаётся - ни в ответе самой ручки, ни в отчёте,
  ни где-либо ещё в контракте (см. "Поведение").
- **`POST .../finish`** - `201` с `TrainingReportResponse` и заголовком `Location`
  (`/sessions/{id}/report`).
- **`POST .../restart`** - `200`, `TrainingSessionResponse` в исходном состоянии
  (`status = CREATED`, `answeredCount = 0`, `totalQuestions` не изменился). Работает только на
  завершённой сессии - на незавершённой `409`.
- **`GET .../report`** - `200`, `TrainingReportResponse`.
- **`DELETE /sessions/{sessionId}`** - `204`, пустое тело.

## Поведение

- **Создание сессии расходует квоту тренировок.** Прежде чем подбирать вопросы (и тем более
  звать LLM), бэкенд проверяет остаток тренировок по тарифу - если он исчерпан,
  `402` с деталью `Training quota exhausted`. Настоящее списание - атомарное, происходит уже в
  транзакции, которая сохраняет сессию; подробности механики квот - в `docs/billing-api.md`.
- **Создание сессии сразу собирает все вопросы.** `POST /sessions` подбирает их из банка по
  (профессия, навык, уровень), исключая вопросы, которые пользователь уже видел в любой из
  своих прошлых сессий, и добирает недостающие до `questionCap` (10) одним батч-вызовом
  LLM-агента, выбранного по уровню сложности. Генератору дополнительно передаются уже
  отобранные из банка вопросы - чтобы не дублировать их по смыслу. Вопросов в сессии может
  оказаться меньше `questionCap` (банк пуст, LLM вернула меньше запрошенного), но не меньше
  `minAnswersToFinish` (3): набралось меньше - `503`, сессия не создаётся. Иначе получилась бы
  сессия-тупик, которую нельзя ни продолжить, ни завершить. Пользователю вопросы всё равно
  отдаются по одному через `.../questions/next`.
- **Вопросы кончились - можно взять ещё пачку.** `POST .../questions/more` дописывает в ту же
  сессию следующие `questionCap` (10) вопросов - это альтернатива разбору, а не отдельная
  тренировка: `orderIndex` продолжает сквозную нумерацию, а отчёт в конце охватит все
  отвеченные вопросы сессии. Вопросы именно новые: банк по-прежнему отдаёт только не виденное
  пользователем ни в одной его сессии, а генератору передаются тексты всех уже заданных
  вопросов, чтобы он не повторялся. Ручка требует, чтобы неотвеченных вопросов не осталось
  (иначе `409` `Unanswered questions left`) и чтобы в сессии было меньше `maxQuestions` (50)
  вопросов (иначе `409` `Question limit reached`); последняя пачка перед потолком может быть
  короче 10. Доступна только на платном тарифе - на `FREE`, включая истёкший PRO/MAX, `403` с
  деталью `Paid plan required` (эта проверка идёт раньше остальных); саму квоту тренировок добор
  не расходует (подробнее - `docs/billing-api.md`). **Придумать новые вопросы удалось не всегда:** банк по паре навык/уровень
  исчерпан, а LLM не дала ни одного пригодного вопроса - тогда `409` с деталью
  `No new questions available`, сессия не меняется, и дальше остаётся только `finish`. Это
  штатный ответ, а не сбой AI-сервиса: `503` здесь не отдаётся.
- **Пройти заново - это перезапуск той же сессии.** `POST .../restart` возвращает завершённую
  тренировку в исходное состояние: вопросы и их эталонные ответы остаются на месте (те же
  тексты, тот же порядок, тот же `sessionId`), а ответы, поразборный фидбэк и отчёт стираются
  безвозвратно - `GET .../report` после этого отвечает `404`, пока тренировка не будет
  завершена снова. Вопросов в перезапущенной сессии столько, сколько осталось после прошлого
  завершения (неотвеченные при `finish` удаляются). Незавершённую сессию перезапускать нечего -
  `409`. Перезапуск тоже расходует квоту тренировок - на любом тарифе, включая FREE - и делает
  это без LLM и без предварительной мягкой проверки: пуст остаток - `402` с деталью
  `Training quota exhausted` (подробнее - `docs/billing-api.md`).
- **Уточняющих вопросов нет.** Каждый вопрос сессии самостоятелен: один вопрос - один
  ответ - одна оценка - один фидбэк, без деления на основные и уточняющие и без обращения к
  LLM по ходу тренировки. `.../questions/next` просто возвращает следующий неотвеченный вопрос
  по `orderIndex`.
- **`.../questions/next` идемпотентен.** Повторный вызов, пока текущий вопрос не отвечен,
  вернёт тот же вопрос - это и точка возврата: прервал тренировку и вернулся, получишь тот же
  вопрос, на который нет ответа. Вопросы в сессии кончились (все отвечены) или сессия уже
  завершена - `409`, дальше только `finish`.
- **Оценок по ходу тренировки нет.** `POST .../questions/{questionId}` только сохраняет текст
  ответа и отвечает `204` без каких-либо `score`/`feedback`. Весь фидбэк формируется одним
  пакетом при завершении. Повторно ответить на уже отвеченный вопрос нельзя - `409`. Как
  только сохранён первый ответ, статус сессии переходит из `CREATED` в `IN_PROGRESS`.
- **Проверка принадлежности вопроса.** Помимо владельца, у отправки ответа, у просмотра
  эталонного ответа и у отзыва на вопрос проверяется, что `questionId` действительно относится
  к сессии, указанной в пути `sessionId` - если нет, это `409` (а не `404`/`403`), потому что
  сам вопрос существует и доступен, просто запрос обратился не к той сессии.
- **Отзыв на разбор - append-only и ни на что не влияет.** Обе ручки (`.../feedback` у вопроса
  и у отчёта) просто добавляют строку в `training.user_feedback` (`question_id = NULL` у отзыва
  на отчёт) и ничего не читают и не пересчитывают в ответ - это сырьё для ручного улучшения
  вопросов и промптов разборов, а не часть продуктового контракта: ни на балл, ни на текст
  фидбэка, ни на что-либо ещё в отчёте отзыв не влияет. Отзыв не отдаётся обратно ни в одном
  ответе API - ни в самой ручке фидбэка, ни в отчёте, ни отдельным списком где-либо ещё, читать
  свой прошлый отзыв через API нельзя. В отличие от отправки ответа на вопрос, отзыв на вопрос
  не требует, чтобы вопрос уже был отвечен, и не проверяет статус сессии - оставить отзыв можно
  в любой момент, пока вопрос физически существует в БД (после `finish` неотвеченные вопросы
  удаляются - отзыв на такой вопрос после этого момента отвечает `404`, как и просмотр его
  эталонного ответа). Отзыв на отчёт требует, чтобы отчёт уже существовал - `finish` ещё не
  вызывался или сессия не найдена - `404`. Перезапуск (`.../restart`) прошлые отзывы не
  трогает: строки в `training.user_feedback` остаются в БД даже после того, как сам отчёт,
  к которому они относились, стёрт перезапуском.
- **Эталонный ответ - по требованию, с кешем.** У вопроса из банка эталон обычно уже
  подготовлен куратором контента и копируется в вопрос сессии при её создании
  (`content.question_bank.reference_answer`). Если для конкретного вопроса банка эталона нет
  (поле пустое) - как и у полностью сгенерированного вопроса - эталон создаёт LLM-агент
  `training-reference-answer` по первому запросу к `.../reference-answer` и сохраняет его в
  `training.question.reference_answer`, поэтому повторный показ того же вопроса ничего не
  стоит: нового обращения к LLM не будет. Пустой ответ от LLM - `503`, ничего не кешируется,
  следующий запрос попробует сгенерировать заново. В отличие от отправки ответа, эта ручка не
  проверяет статус сессии и не требует, чтобы вопрос уже был отвечен: эталон можно посмотреть
  и до своего ответа, и после завершения тренировки - пока вопрос физически существует в БД
  (см. следующий пункт).
- **Неотвеченные вопросы при завершении удаляются.** Всё, что осталось без ответа, при
  `finish` выбрасывается из БД и в отчёт не попадает - вместе с вопросом пропадает и его
  эталонный ответ; `.../reference-answer` на такой вопрос после этого момента отвечает `404`.
- **Завершение (`finish`) требует минимум 3 отвеченных вопроса.** Если отвечено меньше - `409`.
- **Оценивание в отчёте идёт по каждому отвеченному вопросу отдельно.** При `finish` бэк
  отдаёт агенту-оценщику (`training-reviewer`) весь список отвеченных вопросов с ответами
  разом и получает по каждому оценку (`score`, 1-5) и текстовый разбор (`feedback`). Агент
  один на все уровни сложности: оценка не сравнивает ответ с "ожиданиями от грейда", а меряет
  его полноту относительно конкретно заданного вопроса.
- **Плохой отчёт не сохраняется.** Если LLM не дала внятный итоговый фидбэк (короче 10
  символов) или разобрала меньше половины отвеченных вопросов, бэк повторяет запрос к LLM один
  раз; если и повтор оказался таким же вырожденным - `finish` отвечает `503`, а сессия
  остаётся незавершённой, запрос можно повторить позже. Отдельные невалидные оценки внутри в
  целом пригодного отчёта (балл вне 1-5, пустой разбор, повторная оценка того же вопроса)
  отбрасываются молча: такой вопрос останется в отчёте без `score`/`feedback`, если общий
  порог "не меньше половины" при этом выдержан.
- **Средний балл считается на бэке**, а не берётся из LLM целиком: это среднее по оценкам
  вопросов, получивших `score`, округлённое до одного знака после запятой (диапазон 1.0-5.0).
- **Сессия завершается один раз.** После `finish` статус - `COMPLETED`, проставляется
  `completedAt`. Повторный `finish` на уже завершённой сессии - `409`, отчёт не
  пересобирается; посмотреть его можно только через `GET .../report`. Два параллельных
  `finish` тоже дадут ровно один отчёт: проигравший запрос получит `409`.
- **`answeredCount`** в `TrainingSessionResponse` считает все отвеченные вопросы сессии -
  деления на основные и уточняющие в тренажёре нет.
  Рядом `totalQuestions` - сколько вопросов в сессии сейчас; на прогресс "N / M" в UI надо
  брать именно его, а не `questionCap`: после добора вопросов в сессии больше 10, а после
  завершения - только отвеченные.
- **Удаление** - физическое: сессия удаляется вместе со всеми вопросами и отчётом (не soft
  delete, в отличие от домена пользователей).

| Код | Когда |
|---|---|
| `400` | невалидное тело запроса: пустой или длиннее 100 символов `skill`/`profession` (в `CreateSessionRequest` и в `NormalizeInputRequest`), отсутствующий/невалидный `level`, пустой `answerText`, отсутствующий `vote`, `reasons` длиннее 10 элементов или с элементом длиннее 100 символов, `comment` длиннее 2000 символов (в `FeedbackRequest`), битый JSON, неверный тип path-параметра (например, `sessionId`/`questionId` не UUID); отсутствующий обязательный query-параметр `query` у `/suggest/professions` и `/suggest/skills` (`profession` у `/suggest/skills` при этом необязателен) |
| `401` | нет валидного access-токена (ставит Security-фильтр, тело пустое) |
| `402` | исчерпана квота тренировок - остаток по тарифу `0` (`POST /sessions`, `POST .../restart`); подробнее - `docs/billing-api.md` |
| `403` | вопрос, к которому обращается запрос (отправка ответа, просмотр эталонного ответа или отзыв на вопрос), принадлежит другому пользователю; добор вопросов (`POST .../questions/more`) на тарифе `FREE`, включая истёкший PRO/MAX - деталь `Paid plan required` |
| `404` | сессия или вопрос не найдены (в т.ч. чужие - они ищутся сразу с учётом пользователя; для эталонного ответа и для отзыва на вопрос сюда же относится вопрос, физически удалённый как неотвеченный после завершения сессии); отчёт ещё не сформирован (`GET .../report` и `POST .../report/feedback` - у обеих `Report not found`) |
| `409` | сессия уже завершена (в т.ч. если её завершил параллельный запрос); вопросы в сессии кончились - все отвечены; вопрос уже отвечен; вопрос не принадлежит указанной в пути сессии (в т.ч. при отзыве на вопрос); отвечено меньше 3 вопросов при попытке завершить; при доборе вопросов - остались неотвеченные (`Unanswered questions left`), достигнут потолок в 50 вопросов (`Question limit reached`) или новых вопросов по навыку и уровню больше нет (`No new questions available`); при перезапуске - тренировка ещё не завершена (`Session is not finished`) |
| `422` | `POST /sessions`: навык или профессия не распознаны (словарю неизвестны, и LLM-агент `input-normalizer` их не понял) - детали `Skill not recognized` (проверяется первым) / `Profession not recognized`, `message` - `Unprocessable content.` |
| `429` | превышен лимит частоты запросов с одного IP: по 60 запросов в минуту отдельно на `/suggest/professions` и на `/suggest/skills`, 10 запросов в минуту на `/normalize` - три независимых счётчика, отдельных друг от друга и от почтовых ручек `auth` |
| `503` | AI-сервис недоступен или вернул непригодный ответ - при создании сессии (банк и LLM вместе дали меньше 3 вопросов), при просмотре эталонного ответа (LLM вернула пустой ответ), при завершении сессии (пустой/слишком короткий итоговый фидбэк либо разобрано меньше половины вопросов - после одного повторного вызова LLM) и при распознавании ввода на `/normalize` |

`503` отдаётся глобальным обработчиком `LlmException` (`AI service unavailable.`) - на
ручках, дёргающих LLM: `POST /sessions`, `POST .../questions/more` (только если AI-сервис
недоступен; пустой список пригодных вопросов от живой LLM - это `409`, см. "Поведение"),
`GET .../reference-answer`, `POST .../finish` и `POST /normalize`. У `POST .../questions/next` LLM не задействован вовсе, поэтому
`503` у неё не бывает.
